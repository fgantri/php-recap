SQL Cheat Sheet

MySQL/MariaDB dialect. You describe the result; the planner decides how to get it.

Connecting

sudo service mariadb start
mysql -u root                       # local root, usually no password
mysql -u root -p myapp              # with password, straight into a database
mysql -u root myapp < dump.sql      # run a file

SHOW DATABASES;  USE myapp;  SHOW TABLES;
DESCRIBE notes;          -- columns, types, nullability, keys
SHOW CREATE TABLE notes; -- the full definition, including indexes and FKs
SHOW INDEX FROM notes;

Types — the six you'll use

TypeForNote
INTIDs, counts4 bytes. BIGINT when you might exceed 2.1 billion
VARCHAR(255)Names, emails, titlesThe limit is characters, not bytes
TEXTBodies, articlesNo practical limit; cannot have a default
BOOLEANFlagsAlias for TINYINT(1); stores 0/1
DATETIME / TIMESTAMPPoints in timeTIMESTAMP converts to UTC and has a 2038 limit
DECIMAL(10,2)MoneyNever FLOAT — binary floats cannot represent 0.10 exactly

DDL

CREATE DATABASE myapp CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci;

CREATE TABLE users (
    id         INT UNSIGNED AUTO_INCREMENT PRIMARY KEY,
    name       VARCHAR(255) NOT NULL,
    email      VARCHAR(255) NOT NULL,
    created_at TIMESTAMP    NOT NULL DEFAULT CURRENT_TIMESTAMP,
    UNIQUE KEY users_email_unique (email)
);

CREATE TABLE notes (
    id         INT UNSIGNED AUTO_INCREMENT PRIMARY KEY,
    user_id    INT UNSIGNED NOT NULL,
    body       TEXT         NOT NULL,
    created_at TIMESTAMP    NOT NULL DEFAULT CURRENT_TIMESTAMP,
    CONSTRAINT notes_user_id_foreign
        FOREIGN KEY (user_id) REFERENCES users(id) ON DELETE CASCADE
);

ALTER TABLE notes ADD COLUMN status VARCHAR(20) NOT NULL DEFAULT 'draft';
ALTER TABLE notes ADD INDEX notes_user_id_index (user_id);
ALTER TABLE notes DROP COLUMN status;

Always utf8mb4. MySQL's utf8 is a three-byte imitation that cannot store emoji or some CJK characters. The foreign-key column type must match the referenced key exactly, UNSIGNED included.

Reading

SELECT id, title FROM posts;              -- name columns; * breaks on schema change
SELECT * FROM posts WHERE id = 1;         -- SQL uses a single = to compare
SELECT * FROM posts WHERE id IN (1,2,3);
SELECT * FROM posts WHERE title LIKE '%blog%';   -- leading % cannot use an index
SELECT * FROM posts WHERE published_at IS NOT NULL;   -- never = NULL
SELECT * FROM posts ORDER BY created_at DESC LIMIT 10 OFFSET 20;
SELECT DISTINCT author FROM posts;
OperatorMeaning
= <> < > <= >=Comparison. <> is "not equal"
AND OR NOTLogic. Parenthesise mixed AND/OR
IS NULL / IS NOT NULLThe only way to test null — = NULL is never true
BETWEEN a AND bInclusive at both ends
LIKE / NOT LIKE% = any run, _ = one character

Writing

INSERT INTO posts (title, body) VALUES ('First', 'Hello');
INSERT INTO posts (title) VALUES ('A'), ('B'), ('C');       -- one round trip

UPDATE posts SET title = 'New' WHERE id = 1;   -- ALWAYS have a WHERE
DELETE FROM posts WHERE id = 1;

SELECT LAST_INSERT_ID();
Before any UPDATE or DELETE

Run it as a SELECT with the same WHERE first and look at the row count. UPDATE posts SET title='x' without a WHERE rewrites every row in the table, and there is no undo.

In a client, SET SQL_SAFE_UPDATES = 1; refuses unqualified updates. Worth having on.

Joins

SELECT notes.id, notes.body, users.name
FROM notes
JOIN users ON users.id = notes.user_id;              -- INNER: matches only

SELECT users.name, notes.body
FROM users
LEFT JOIN notes ON notes.user_id = users.id;         -- all users, notes if any
JoinReturnsUse for
INNER JOINOnly rows matching on both sidesThe default. "Notes with their author"
LEFT JOINAll left rows; nulls where no match"All users, and their notes if any"
RIGHT JOINMirror of LEFTRare — reorder the tables instead

An orphan row silently disappears from an INNER JOIN. That is the quiet damage referential integrity prevents — the report is simply wrong, with no error.

Aggregates

SELECT COUNT(*) FROM notes;
SELECT user_id, COUNT(*) AS total
FROM notes
GROUP BY user_id
HAVING COUNT(*) > 5           -- HAVING filters GROUPS; WHERE filters ROWS
ORDER BY total DESC;

WHERE runs before grouping, HAVING after. COUNT(*) counts rows; COUNT(col) skips nulls. Others: SUM, AVG, MIN, MAX.

Indexes

CREATE INDEX notes_user_id_index ON notes (user_id);
CREATE UNIQUE INDEX users_email_unique ON users (email);
CREATE INDEX notes_user_created ON notes (user_id, created_at);   -- composite
DROP INDEX notes_user_id_index ON notes;

EXPLAIN SELECT * FROM notes WHERE user_id = 1;
IndexWhy
Every foreign keyJoins and cascade checks scan without one. MySQL adds these automatically; other engines don't
Columns in WHEREThe whole point
Columns in ORDER BYAvoids sorting the result set
Columns needing uniquenessA unique index enforces the rule and speeds lookups

Leftmost prefix rule: an index on (a, b, c) serves queries filtering on a, or a,b, or a,b,c — but not b alone. Column order is a design decision.

Indexes are not free. Every write must update every index. Index what you filter, join and sort on — not everything.

Reading EXPLAIN

typeMeaning
const / eq_refOne row via a unique key. Best possible
refIndex used, several rows match. Good
rangeIndex range scan. Fine
indexWhole index scanned. Suspicious
ALLFull table scan. Fix this if the table is large

Also watch rows (how many the planner expects to examine) and Extra — Using filesort and Using temporary both mean work an index could have avoided.

Transactions

START TRANSACTION;
UPDATE accounts SET balance = balance - 100 WHERE id = 1;
UPDATE accounts SET balance = balance + 100 WHERE id = 2;
COMMIT;   -- or ROLLBACK;
$pdo->beginTransaction();
try {
    …
    $pdo->commit();
} catch (Throwable $e) {
    $pdo->rollBack();
    throw $e;
}

Either all of it applies or none of it does. Required whenever two changes must agree. Note that DDL (CREATE, ALTER) causes an implicit commit in MySQL — you cannot roll back a schema change.

Cascade options

ON DELETEEffectRight for
CASCADEDelete the children tooNotes belonging to a user
RESTRICTRefuse while children existInvoices — you may be legally required to keep them
SET NULLBlank the reference (column must be nullable)A post whose author left, but which stays published

There is no default correct answer. It depends on what the data means.

Backup

mysqldump -u root myapp > backup.sql
mysqldump -u root myapp notes > notes.sql
mysql -u root myapp < backup.sql

Take one before experimenting with DROP or cascades. It costs a second.
