Security Cheat Sheet

Almost everything here is one idea wearing different clothes.

The law

Data must never be able to become code.

Every injection vulnerability is a failure of that boundary. Learn the shape once and you recognise the whole family — including ones invented after you read this.

The pattern in the "Never" column: every failed defence tries to clean the data. Every working defence separates data from structure, so cleaning is unnecessary.

SQL injection

// VULNERABLE — the query and the input are one string
$id = $_GET['id'];
$db->query("SELECT * FROM posts WHERE id = $id");
// ?id=1 OR 1=1          → the whole table
// ?id=1; DROP TABLE users → gone

// SAFE — two separate journeys
$db->query('SELECT * FROM posts WHERE id = :id', ['id' => $_GET['id']]);

Why separation works: prepare() sends the SQL template alone; MySQL parses it and fixes the query's structure. execute() then sends values into slots in an already-planned query. They are never parsed as SQL, because parsing already finished.

Placeholders bind values, not identifiers

You cannot parameterise a table name, column name, or ORDER BY direction. When those must be dynamic, check against an explicit allowlist:

$allowed = ['title', 'created_at', 'id'];
$sort = in_array($_GET['sort'] ?? '', $allowed, true) ? $_GET['sort'] : 'id';
$dir  = ($_GET['dir'] ?? '') === 'desc' ? 'DESC' : 'ASC';
$db->query("SELECT * FROM posts ORDER BY {$sort} {$dir}");

Safe because the interpolated values can only ever be strings you wrote. Never validate this with a regex.

XSS — escape per context

ContextCorrect escaping
<p>HERE</p>htmlspecialchars($v, ENT_QUOTES, 'UTF-8')
value="HERE"Same — and quote the attribute
?q=HEREurlencode($v)
<script>var x = HERE</script>json_encode($v, JSON_HEX_TAG|JSON_HEX_AMP)
href="HERE"Escape and allowlist the scheme — javascript: is a valid URL
Inside CSSDon't. Use a class name

htmlspecialchars does not protect inside a <script> block — HTML entities aren't decoded there, and </script> inside a JS string still closes the tag.

You do not need a <script> tag to run JavaScript: <img src=x onerror=…> is enough. This is why writing your own HTML sanitiser is a mistake — use HTMLPurifier, or accept Markdown instead of HTML.

CSRF

A third-party page causes the user's browser to submit a request to your site. The browser attaches cookies automatically, so the request is fully authenticated — the attacker never needs to see the response.

// generate once per session
$_SESSION['csrf'] ??= bin2hex(random_bytes(32));

// in every state-changing form
<input type="hidden" name="_token" value="<?= e($_SESSION['csrf']) ?>">

// verify before acting — timing-safe comparison
if (! hash_equals($_SESSION['csrf'], $_POST['_token'] ?? '')) {
    abort(419);
}
TokenUnpredictable, bound to the session, verified on every state change
SameSite=LaxBrowser withholds the cookie on cross-site POSTs. Good default, not sufficient alone
VerbsNever change state on GET — that's what makes the attack trivial
hash_equalsConstant-time. === leaks length and prefix through timing

Authentication

$hash = password_hash($plain, PASSWORD_DEFAULT);   // bcrypt/argon2, salt included

if (password_verify($plain, $user['password'])) {
    session_regenerate_id(true);                   // prevents session fixation
    $_SESSION['user_id'] = $user['id'];
}
Non-negotiable

Never md5, sha1, or sha256 for passwords — they are designed to be fast, which is exactly wrong. Never your own salting scheme; password_hash generates and stores the salt for you. Never === on hashes — use password_verify.

Store the hash in VARCHAR(255), not 60 — the algorithm's output length changes between PHP versions, and a too-short column silently truncates, locking everyone out.

Sessions

session_set_cookie_params([
    'httponly' => true,      // JavaScript cannot read it — blunts XSS cookie theft
    'secure'   => true,      // HTTPS only
    'samesite' => 'Lax',     // CSRF mitigation
    'path'     => '/',
]);
session_start();

Regenerate the id on login and on privilege change. Destroy it fully on logout — session_destroy() plus clearing $_SESSION plus expiring the cookie.

Authentication vs authorization

AuthenticationWho are you?Login, sessions, tokens401
AuthorizationMay you do this?Ownership, roles, permissions403
 
$note = $db->query('SELECT * FROM notes WHERE id = :id', ['id' => $id])->fetch();

if (! $note)                                  { abort(404); }   // does not exist
if ((int) $note['user_id'] !== $currentUserId) { abort(403); }   // not yours

IDOR — Insecure Direct Object Reference — is what you get without that second check. Change the id in the URL, read someone else's data. The fix is checking ownership on every request; it is never hiding or obfuscating the id.

403 or 404? A real trade-off

Returning 403 tells an attacker the record exists. For a notes app that leak is trivial and 403 is clearer. For anything where existence itself is sensitive — medical records, private repositories, HR files — return 404 for both and log the distinction internally. GitHub does exactly this.

Also note the (int) cast: with PDO emulating prepares, integer columns arrive as strings, and '1' !== 1 would reject the rightful owner.

Configuration and secrets

Secrets in .envNever committed. .env.example with dummy values is committed
.env outside the web rootOr unreachable by URL. Leaked .env files are a top cause of breaches
chmod 600Only the owner may read it

Headers worth sending

header("Content-Security-Policy: default-src 'self'");
header('X-Content-Type-Options: nosniff');
header('Referrer-Policy: strict-origin-when-cross-origin');
header('Strict-Transport-Security: max-age=31536000; includeSubDomains');

CSP is defence in depth: even if you miss an escape, the browser refuses to run injected inline script. Worth adding once and keeping.

Pre-deploy checklist

  • Every query parameterised — no user input in any SQL string, anywhere
  • Every user-derived output escaped, with the right function for its context
  • Every state-changing form carries and verifies a CSRF token
  • Every record fetched by id is ownership-checked before rendering
  • Passwords via password_hash / password_verify; column is VARCHAR(255)
  • Session cookie is httponly, secure, samesite; id regenerated on login
  • display_errors off, log_errors on, error log monitored
  • Only public/ is inside the document root
  • .env not committed, not readable, permissions 600
  • No destructive action reachable by GET
  • File uploads: validate by content, store outside the web root, never trust the filename
  • Dependencies audited — composer audit
