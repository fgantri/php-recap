Four upgrades

1 — A Response object

You have a Request. Right now the response side is scattered: http_response_code() here, header() there, echo somewhere else. Make it a value too.

final class Response
{
    public function __construct(
        public readonly string $body = '',
        public readonly int    $status = 200,
        public readonly array  $headers = [],
    ) {}

    public static function html(string $body, int $status = 200): self
    {
        return new self($body, $status, ['Content-Type' => 'text/html; charset=utf-8']);
    }

    public static function json(array $data, int $status = 200): self
    {
        return new self(json_encode($data, JSON_THROW_ON_ERROR), $status,
            ['Content-Type' => 'application/json']);
    }

    public static function redirect(string $to, int $status = 303): self
    {
        return new self('', $status, ['Location' => $to]);
    }

    public function send(): void
    {
        http_response_code($this->status);
        foreach ($this->headers as $name => $value) {
            header("{$name}: {$value}");
        }
        echo $this->body;
    }
}
Why this is a bigger change than it looks

Controllers now return instead of echo. That single shift means a controller is a pure function from Request to Response — no side effects, nothing written to output. Which means:

  • You can test it: call it, assert on $response->status. No server, no browser, no output buffering.
  • You can wrap it: middleware can inspect or modify the response on its way out.
  • The "headers already sent" error becomes structurally impossible — nothing outputs until send().

This is PSR-7's core design, and it is why every modern PHP framework converged on it.

2 — A middleware pipeline

interface Middleware
{
    public function handle(Request $request, Closure $next): Response;
}

final class RequireAuth implements Middleware
{
    public function handle(Request $request, Closure $next): Response
    {
        if (! isset($_SESSION['user_id'])) {
            return Response::redirect('/login');      // short-circuit — $next never called
        }

        return $next($request);                       // carry on down the chain
    }
}

The pipeline itself is the interesting part — build it with array_reduce, walking the list backwards to nest the closures:

function pipeline(array $middleware, Closure $destination): Closure
{
    return array_reduce(
        array_reverse($middleware),
        fn (Closure $next, Middleware $layer) =>
            fn (Request $request) => $layer->handle($request, $next),
        $destination
    );
}
Foundation — This is the onion, and it is just closures

Each layer receives the request and the rest of the pipeline as a callable. It may act before calling $next, after, both, or refuse to call it at all — which is what short-circuiting is.

Execution order is an onion: A → B → C → controller → C → B → A. A layer that starts a timer before $next and logs after it has measured everything inside, with no coordination.

This is the callback pattern from Lesson 0012, arranged in a chain. Laravel's Illuminate\Pipeline is the same array_reduce. Express's app.use(), Django's middleware, and PSR-15 are all this shape. Once you have written it, framework middleware stops being a configuration item and becomes something you can reason about.

3 — A container

final class Container
{
    private array $bindings = [];
    private array $instances = [];

    public function bind(string $key, Closure $factory): void
    {
        $this->bindings[$key] = $factory;
    }

    public function singleton(string $key, Closure $factory): void
    {
        $this->bind($key, function () use ($key, $factory) {
            return $this->instances[$key] ??= $factory($this);
        });
    }

    public function resolve(string $key): mixed
    {
        if (! isset($this->bindings[$key])) {
            throw new RuntimeException("Nothing bound for [{$key}]");
        }

        return ($this->bindings[$key])($this);
    }
}
$container->singleton(Database::class, fn () => new Database($config['database']));

$db = $container->resolve(Database::class);

That is roughly forty lines and it is the core of Laravel's service container — a map of keys to factory closures, with an instance cache for singletons. What Laravel adds is autowiring: reading a constructor's type hints via reflection and resolving them recursively, so you rarely register anything by hand.

What the container actually buys you

It replaces $db arriving invisibly through shared scope with a controller that declares what it needs. The dependency becomes visible in the signature, and — the real payoff — you can substitute a fake in a test:

$container->bind(Database::class, fn () => new InMemoryDatabase());

Your controller is now testable without MySQL running. That property is the entire justification for dependency injection, and it is much easier to appreciate having felt the shared-variable version first.

4 — Actual tests

No framework needed. A plain PHP file and assert is enough to prove the point:

tests/router.test.php
<?php

declare(strict_types=1);

require __DIR__ . '/../src/bootstrap.php';

$tests = 0;
$failed = 0;

function test(string $name, callable $fn): void
{
    global $tests, $failed;
    $tests++;

    try {
        $fn();
        echo "  ✓ {$name}\n";
    } catch (Throwable $e) {
        $failed++;
        echo "  ✕ {$name}\n    {$e->getMessage()}\n";
    }
}

test('captures a route parameter', function () use ($router) {
    $match = $router->match(new Request('GET', '/notes/17'));

    if ($match->params['id'] !== '17') {
        throw new Exception('expected id 17, got ' . var_export($match->params, true));
    }
});

test('prefers a literal route over a dynamic one', function () use ($router) { … });
test('405 when the path matches but the method does not', … );
test('query string is excluded from matching', … );
test('anchors prevent /evil/notes/17 matching', … );

echo "\n{$tests} tests, {$failed} failed\n";
exit($failed === 0 ? 0 : 1);   // exit code — Lesson 0003
php tests/router.test.php; echo "exit: $?"

Note the exit code. That is what makes this runnable in CI — a test script that always exits 0 tells a pipeline nothing, which is the Lesson 0003 point arriving with consequences.
