The schema, first

mysql -u root

CREATE DATABASE notes_app CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci;
USE notes_app;

CREATE TABLE users (
    id         INT UNSIGNED AUTO_INCREMENT PRIMARY KEY,
    name       VARCHAR(255) NOT NULL,
    email      VARCHAR(255) NOT NULL,
    password   VARCHAR(255) NOT NULL,          -- 255, never 60
    created_at TIMESTAMP    NOT NULL DEFAULT CURRENT_TIMESTAMP,
    UNIQUE KEY users_email_unique (email)      -- the constraint, not a check
);

CREATE TABLE notes (
    id         INT UNSIGNED AUTO_INCREMENT PRIMARY KEY,
    user_id    INT UNSIGNED NOT NULL,          -- type must match exactly
    body       TEXT         NOT NULL,
    created_at TIMESTAMP    NOT NULL DEFAULT CURRENT_TIMESTAMP,
    updated_at TIMESTAMP    NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
    CONSTRAINT notes_user_id_foreign
        FOREIGN KEY (user_id) REFERENCES users(id) ON DELETE CASCADE,
    INDEX notes_user_id_created (user_id, created_at)
);

Four decisions worth being able to defend: the unique index on email (constraint, not application check — Lesson 0021); VARCHAR(255) for the hash (Lesson 0023); ON DELETE CASCADE because notes belong to their user; and the composite index (user_id, created_at) because the main query filters by user and sorts by date — leftmost prefix, Lesson 0018.

Browsers only send GET and POST

HTML forms cannot issue PATCH or DELETE. The universal workaround — used by Laravel, Rails and Symfony alike — is a hidden field:

<form method="POST" action="/notes/17">
    <input type="hidden" name="_method" value="DELETE">
    <input type="hidden" name="_token" value="<?= e($token) ?>">

Your router reads $_POST['_method'] and overrides the verb. Only ever upgrade from POST — honouring _method on a GET would let a link perform a delete, which is precisely the crawler disaster from Lesson 0005.

Requirement 8 is where people get this wrong

It is easy to check ownership on the page that displays a note and forget the one that deletes it. An attacker does not need your edit form — they can POST directly:

curl -X POST localhost:8888/notes/42 \
     -d '_method=DELETE&_token=...' -b 'PHPSESSID=my-own-session'

Every route that touches a record by id needs the check. Not the ones with forms — all of them. This is the single most common real-world IDOR, and it is why frameworks push authorization into policies applied declaratively rather than remembered per-controller.

The pieces worth seeing

src/auth.php
function attempt(Database $db, string $email, string $password): bool
{
    $user = $db->query('SELECT * FROM users WHERE email = ?', [$email])->fetch();

    // verify even when no user exists, so timing does not reveal registered emails
    $hash = $user['password'] ?? '$2y$10$invalidinvalidinvalidinvalidinvalidinvalidinvalidinvalidin';

    if (! password_verify($password, $hash) || ! $user) {
        return false;
    }

    session_regenerate_id(true);
    $_SESSION['user_id'] = (int) $user['id'];

    return true;
}

That dummy hash is worth understanding: without it, a login attempt for an unknown email returns faster than one for a known email, because password_verify never runs. Timing alone then reveals which addresses are registered. Small detail, real leak.

src/csrf.php
function csrf_token(): string
{
    return $_SESSION['csrf'] ??= bin2hex(random_bytes(32));
}

function verify_csrf(): void
{
    if (! hash_equals(csrf_token(), $_POST['_token'] ?? '')) {
        abort(419);
    }
}

Acceptance tests

Work every line. Several of these are the ones people skip, and they are the ones that matter.

# --- functionality ---
Register two users. Create notes as each.
Log in as user 1 → /notes shows ONLY user 1's notes.
Create a note → redirected, flash message shown, refresh does NOT duplicate it.
Edit and delete your own note. Both work.

# --- authorization: the important part ---
As user 1, visit /notes/{a-note-belonging-to-user-2}     → 403 (or 404, decided deliberately)
As user 1, POST _method=DELETE to user 2's note id       → 403, and the note SURVIVES
Log out, visit /notes                                    → redirected to /login
Log in, visit /login                                     → redirected to /notes

# --- security ---
Submit a form with _token removed                        → 419
Create a note whose body is <img src=x onerror=alert(1)>
  → view source: you MUST see &lt;img
Register with an email that already exists               → clean error, not a 500
Register the same email from two terminals at once       → the unique index holds
Note id ?id=1 OR 1=1 in any URL                          → no extra data, ever

# --- data ---
DELETE FROM users WHERE id = 1;   → user 1's notes are gone too (cascade)
INSERT a note with user_id = 999  → rejected by the foreign key

Specifically: every route that takes an id, checked for the ownership test; every form, checked for a token; every output, checked for escaping; the login path, checked for user enumeration; and the PDO configuration, checked for the emulated-prepares trap that silently breaks !== comparisons.

Stretch goals

Pagination

LIMIT + OFFSET with page links. Then read Lesson 0018 again and notice why deep offsets get slow — the engine still walks every skipped row.

Search

WHERE body LIKE ? with a bound parameter. Note that a leading % cannot use an index; that limitation is the entire reason full-text search engines exist.

Soft deletes

A deleted_at column and a filter on every read. Feel how easy it is to forget one — that is why frameworks make it a trait with a global scope.

"Remember me"

A long-lived token in its own table, rotated on use. Genuinely subtle to get right, and a good thing to have thought about before you need it.

Ask freely. "How do I redisplay validation errors without losing what they typed?", "is my auth flow actually safe?", "why does my CSRF check fail after logging out and back in?" — that last one has a good answer involving session regeneration, and it catches everyone once.
