Note what is where

public/ is the document root. Everything else sits above it and cannot be reached by URL, no matter what someone types. That is the security property Lesson 0002 and 0007 were building toward, and it is why Laravel and Symfony are laid out this way.

Run it with php -S localhost:8888 -t public — the -t flag sets the document root, mimicking what nginx's root directive does.

The one genuinely new piece: a Request object

Your course read $_SERVER['REQUEST_URI'] directly, and noted that frameworks wrap these in a Request object "which makes code testable — you can construct a fake request without a real HTTP server". Build that.

src/Request.php
<?php

declare(strict_types=1);

final class Request
{
    public function __construct(
        public readonly string $method,
        public readonly string $uri,
        public readonly array  $query = [],
        public readonly array  $body = [],
        public readonly array  $headers = [],
    ) {}

    public static function fromGlobals(): self
    {
        return new self(
            $_SERVER['REQUEST_METHOD'] ?? 'GET',
            $_SERVER['REQUEST_URI']    ?? '/',
            $_GET,
            $_POST,
            function_exists('getallheaders') ? getallheaders() : [],
        );
    }

    public function path(): string
    {
        return parse_url($this->uri, PHP_URL_PATH) ?: '/';
    }

    public function input(string $key, $default = null)
    {
        return $this->body[$key] ?? $this->query[$key] ?? $default;
    }
}
Why this is the highest-value class in the project

It is testable. new Request('GET', '/notes/17') — no server, no browser, no network. Your router can now be tested in milliseconds. That property is the entire reason frameworks do this.

It names the boundary. Superglobals appear in exactly one method, fromGlobals(). Everything downstream receives a typed object. When you later need to handle a JSON body or trust a proxy header, there is one place to change.

readonly means the request cannot be mutated. Nothing downstream can quietly rewrite the URI and confuse everything after it. This is PSR-7's central design decision, and now you know why it was made.

Layouts, replacing partials

Your course used head.php / nav.php / footer.php partials and noted the awkwardness — opening tags in one file and closing them in another. With view() returning a string, there is a better shape:

views/layout.view.php
<!DOCTYPE html>
<html lang="en">
<head>
    <meta charset="utf-8">
    <title><?= e($title ?? 'Notes') ?></title>
    <link rel="stylesheet" href="/style.css">
</head>
<body>
    <nav>
        <a href="/" class="<?= urlIs('/') ? 'active' : '' ?>">Home</a>
        <a href="/notes" class="<?= urlIs('/notes') ? 'active' : '' ?>">Notes</a>
    </nav>

    <main><?= $content ?></main>
</body>
</html>
function render(string $template, array $data = []): string
{
    return view('layout', [
        'title'   => $data['title'] ?? null,
        'content' => view($template, $data),   // inner renders first
    ]);
}

Note <?= $content ?> is deliberately not escaped — it is already-rendered HTML from your own template, not user input. Being able to state why a specific unescaped output is safe is the difference between knowing the rule and understanding it.

Acceptance tests

php -S localhost:8888 -t public

curl -i localhost:8888/                        # 200 home

curl -i localhost:8888/src/Router.php          # 404 — outside the web root
curl -i localhost:8888/../src/Router.php       # 404 — traversal blocked

Then the escaping check. Add a note whose body is <img src=x onerror=alert(1)> to src/data.php, load the page, and view source. You must see &lt;img. If you see a broken-image icon, you have an XSS hole — find the unescaped output.

Stretch goals

A middleware pipeline

Let routes declare middleware. Each receives the Request and a $next callable, and may act before or after. Twenty lines, and it is exactly Laravel's pipeline — pure callbacks from Lesson 0012.

Named routes

$router->get('/notes/{id}', ...)->name('notes.show') plus route('notes.show', ['id' => 3]). Now URLs live in one place and changing a path doesn't break every template.

Constrained parameters

{id:\d+} compiling to (?P<id>\d+). Suddenly /notes/abc is a 404 at the routing layer rather than a confusing error further in.

A first test

No framework needed: a plain PHP file asserting $router->match(new Request('GET', '/notes/17')) returns the right handler and params. This is the payoff for building Request, made visible.

Ask freely. "Why is my 405 returning 404?", "how do I make abort() not fatal on a missing view?", "is my layout approach better or worse than partials?" — that last one is a genuine design question with arguments both ways, and worth talking through.
