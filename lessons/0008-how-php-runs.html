How PHP Actually Runs a File

Four phases, one of which explains parse errors, one explains require, and one explains why PHP forgets everything between requests.

40 minutesWin: parse → opcodes → execute → forget

Your course made a sharp observation in Chapter 02: a parse error blanks the entire page, including correct lines above the mistake, while a runtime error produces output up to the point of failure. That difference is a window into the engine, and today you look through it.

The four phases

PhaseInput → outputWhat can go wrong here
LexCharacters → tokensUnterminated string, stray character
ParseTokens → abstract syntax treeParse error: syntax error, unexpected … — nothing runs
CompileAST → array of opcodesAlmost nothing; some optimisation happens here
ExecuteOpcodes → output, one at a timeUndefined variable, calling a method on null, division by zero

Phases 1–3 process the whole file before phase 4 runs a single instruction. That is the entire explanation. A syntax error on line 90 is caught during parsing, so the echo on line 3 never executes — it was compiled, but the compilation as a whole failed, so there was nothing to run.

See it on your own machine — this is a real command, not a teaching aid:

cd ~/websites/demo
printf '<?php\n$a = 1;\n$b = 2;\necho $a + $b;\n' > ops.php

php -d opcache.enable_cli=1 -d opcache.opt_debug_level=0x10000 ops.php

You get the compiled opcode array printed before the output. Try changing $a + $b to 1 + 2 and run it again: the ADD disappears, replaced by the constant 3. The compiler folded it. PHP optimises your code, which is not something most PHP developers know.

Foundation — if is a conditional jump, and that's all control flow is

Look at the branching snippet in the widget. An if/else compiles to JMPZ — "jump if zero" — plus an unconditional JMP to skip the else-branch. A foreach compiles to FE_RESET, FE_FETCH and a backward jump.

There are no blocks and no indentation at this level. Braces exist entirely for the parser; by execution time everything is a flat list of instructions and jumps between them. This is true of every language you will ever use, and knowing it makes assembly, bytecode and stack traces stop being intimidating.

This answers the question Lesson 0001 left open

If PHP is shared-nothing, how does PHP-FPM reuse processes? Because the process is reused, not the state. MINIT-level things — the engine, loaded extensions, OPcache's compiled opcodes — persist. Everything created during your request is torn down at RSHUTDOWN.

So you get the startup cost amortised and a clean slate. That is a genuinely clever design, and it is why PHP survived a decade of predictions that it wouldn't.

OPcache: skipping phases 1–3

Compiling the same file on every request is waste. OPcache stores the compiled opcode array in shared memory keyed by file path and modification time. On a hit, PHP jumps straight to execution.

php -i | grep -E 'opcache.enable|validate_timestamps'
The deploy trap this creates

In production, opcache.validate_timestamps=0 is common: don't even check whether files changed, just trust the cache. It's faster, and it means deploying new code changes nothing until OPcache is reset.

This is the real cause of "I deployed but the old code is still running". The fix is part of the deploy: reload PHP-FPM, or call opcache_reset(). It is also why atomic symlink deploys (Lesson 0002) can behave oddly — OPcache keys on the resolved path, so the new release genuinely is a different key.

require happens at runtime — and that's the whole trick

Your course noted this in Chapter 07 and built a router on it in Chapter 09. Now you can say exactly why it works:

require is not a compile-time directive like C's #include. It is an opcode, executed in phase 4 like any other. When the VM reaches it, it stops, runs the whole four-phase pipeline on the named file, splices the result into the current execution, and continues.

Three consequences, all of which your course used:

  • The path can be a variable — it's evaluated at execution time. This is what makes require $routes[$uri]; possible, and dispatch is nothing more than that.
  • It can be conditional — inside an if, inside a loop, inside a function.
  • Variables carry across — because it is one continuous execution in one scope. This is why a view can see $filteredBooks without being handed it.
Bridge — this is exactly what a bundler is not allowed to do

JavaScript's import is static: resolved before execution, paths must be literals. That constraint is not an oversight — it is what makes tree-shaking possible. A bundler can prove which exports are unused only because it can see the whole import graph without running anything.

PHP's runtime require buys flexibility and pays for it: no PHP tool can fully determine your dependency graph statically, which is why Composer needs a generated classmap and why static analysers like PHPStan have to work so hard. JavaScript's import() function is the dynamic escape hatch, and it is precisely the thing that creates a separate chunk in your bundle.

Same trade-off, opposite defaults. Now you can see why each language chose as it did.
