Relationships and Integrity

A constraint in the database cannot be bypassed by any application, any migration script, or any developer at a console. That property is why invariants belong as close to the data as possible.

45 minutesWin: push invariants into the database

The three shapes

The inconsistency, and what it costs

Your course made the point by setting a note's user_id to 0. It saved without complaint. There is no user with id 0.

Why orphans are worse than a crash

An orphan record does not announce itself. It makes your data quietly wrong:

  • An INNER JOIN silently drops the row. Your "notes per user" report is short and looks plausible.
  • A dashboard count is low. Nobody notices, because nobody knows the true number.
  • A page shows a blank author name where a name should be.
  • The wrongness compounds — every derived figure inherits it.

A crash gets fixed on Tuesday. A number that is wrong and looks right gets used in a decision.

The constraint

ALTER TABLE notes
ADD CONSTRAINT notes_user_id_foreign
FOREIGN KEY (user_id) REFERENCES users(id)
ON DELETE CASCADE;

Now try user_id = 0 again. The database refuses. Not your validation code — the database, which means it holds no matter what touches the data: a migration, a console session, a second application, a bug in a code path you forgot existed.

Foundation — Two requirements people forget

The types must match exactly. users.id is INT UNSIGNED, so notes.user_id must be INT UNSIGNED too. A mismatch either refuses to create the constraint or causes silent slow conversions on every join. This is the single most common reason a FOREIGN KEY statement errors.

The engine must be InnoDB. MyISAM accepts foreign key syntax and silently ignores it — no error, no constraint, no protection. Ancient tables and cheap hosting still default to it. Check with SHOW TABLE STATUS.

Unique indexes: a rule and a speed-up at once

ALTER TABLE users ADD UNIQUE KEY users_email_unique (email);

A unique index does double duty — it makes lookups by email fast and makes duplicates impossible. That second property is the point.

Why an application check is not enough 
// Two requests arrive at the same moment
$existing = $db->query('SELECT id FROM users WHERE email = ?', [$email])->fetch();
if ($existing) { abort(422); }
$db->query('INSERT INTO users (email) VALUES (?)', [$email]);

Both requests run the SELECT, both find nothing, both INSERT. Two users, one email. This is the identical race condition from Lesson 0016's counter, and no amount of PHP fixes it — the gap between check and insert is where the other request lives.

The unique index closes it, because the check and the write are one atomic operation inside the database. Keep the application check for a friendly error message; rely on the constraint for correctness. Validate for UX, constrain for truth.

Cascade: a decision, not a default

ON DELETEBehaviourRight whenWrong when
CASCADEDelete the children tooNotes belong to their user; deleting the account should remove themThe children have independent value or legal significance
RESTRICTRefuse while children existInvoices — you may be legally required to keep themCleanup becomes impossible without manual work
SET NULLBlank the referenceA post whose author left but which stays publishedThe column is NOT NULL — the constraint can't be created

Your course said it plainly and it is worth repeating: there is no default correct answer. The choice cannot be made from the schema alone — it depends on what the data means and what the business requires. Being asked "should this cascade?" and answering "it depends, and here is what it depends on" is the mark of someone who has thought about it.

Soft deletes, and their real cost

ALTER TABLE notes ADD COLUMN deleted_at TIMESTAMP NULL DEFAULT NULL;

UPDATE notes SET deleted_at = NOW() WHERE id = 5;          -- "delete"
SELECT * FROM notes WHERE deleted_at IS NULL;              -- every read, forever

Nothing is destroyed, deletions are reversible, audit history survives. The cost is that every query must remember the filter — and the one that forgets shows deleted data to a user, silently.

That cost is exactly why frameworks provide this as a feature rather than a convention: Laravel's SoftDeletes trait adds a global scope so the filter cannot be forgotten. Knowing what it is protecting you from is more useful than knowing the trait's name.
