Truth, Comparison, Coercion

Every conditional in every program reduces to a boolean. What PHP does on the way there has caused more production bugs than any other feature of the language.

40 minutesWin: predict any comparison without running it

Your course gave the rule and it is the right one: default to ===. This lesson is about earning that rule — because "just always use three equals" is advice you'll eventually have to break, and you need to know when.

Falsy, exhaustively

These eight values are falsy. Everything else in PHP is truthy. There is no ninth.

false
0
0.0
-0.0
''
'0'
[]
null

The two that catch people: '0' — the one-character string — is falsy, while '0.0', 'false', ' ' and '00' are all truthy. And -1 is truthy, because falsiness is about zero, not about negativity.

The bug this produces, in real code 
$quantity = $_POST['quantity'];   // the user typed 0

if (! $quantity) {
    abort('Please enter a quantity');   // fires for a legitimate 0
}

Same shape with a search term of "0", a house number of 0, a score of 0, or a page offset of 0. The fix is to say what you mean: if ($quantity === '') for "they left it blank", or if (! is_numeric($quantity)) for "that isn't a number". Truthiness is a shortcut, and shortcuts encode assumptions.

Predict the comparison

Retrieval practice, not reading. Predict each result before revealing it — getting one wrong and being surprised is worth more than getting it right.

Loose vs strict
Foundation — PHP 8 fixed the worst of it

Before PHP 8, 0 == 'foo' was true. The rule was "if one side is a number, convert the other to a number", and 'foo' converted to 0. This meant a password check written as $hash == 0 could pass, and it was a genuine source of authentication bypasses.

PHP 8 changed the rule: when comparing a number to a non-numeric string, the number is converted to a string instead. So 0 == 'foo' is now false, and 0 == '0' is still true because '0' is numeric.

Two lessons. First, if you read a pre-2020 PHP article about ==, its examples may simply be wrong now. Second — and more useful — the fact that a language's comparison semantics needed a breaking change to become safe is itself the argument for ===.

When == is actually correct

Rules you can't break are rules you don't understand. Loose comparison is right when you have consciously decided that a type difference is not meaningful:

// Everything from HTTP is a string. This id came from a URL.
if ($note['user_id'] === $_GET['user']) { }   // always false! int vs string

// Correct: convert deliberately, then compare strictly.
if ($note['user_id'] === (int) $_GET['user']) { }
This exact bug is waiting for you in Lesson 0022

Your course's Chapter 14 writes if ($note['user_id'] !== $currentUserId). With PDO's default settings on MySQL, integer columns come back as strings — so '1' !== 1 is true, and the authorization check rejects the rightful owner. Or worse, written the other way round, it lets everyone through.

Two real fixes: cast at the boundary, or set PDO::ATTR_EMULATE_PREPARES => false so the driver returns native types. Lesson 0019 configures PDO properly for exactly this reason. Remember this when you get there.

The null-handling operators

OperatorReads asFires when the left side is
$a ?: $bElvis — "or else"falsy — including 0 and ''. Warns if undefined.
$a ?? $bNull coalescingnull or undefined. Never warns. Usually what you want.
$a ??= $bAssign if not setSame as above, assigning in place.
$a?->b()Nullsafe callReturns null instead of erroring when $a is null.

The distinction is the falsy trap again: $_GET['page'] ?: 1 turns a legitimate page 0 into 1, while $_GET['page'] ?? 1 only supplies the default when the key is genuinely absent. Reach for ?? by default.

Ask your teacher. Worth asking: "show me a real authentication bypass that relied on ==" (the md5 magic-hash trick is a great story), or "what does in_array($x, $arr) do without the third argument?" — the answer involves loose comparison and it surprises everyone.
