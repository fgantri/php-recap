The Filesystem as a Tree

A filename is not a file. Understanding the difference explains permissions, symlinks, document roots, and the most common security bug in file-serving code.

30 minutesWin: what "file not found" really means

Your course gave you the tree: directories inside directories, one root, absolute paths starting at /, relative paths starting from wherever you are. All correct. Now the part it skipped — what a directory actually contains.

A directory is a table of names

A directory does not contain files. It contains a list of names, each paired with a number. That number is an inode, and the inode is where the file really lives.

Three consequences follow immediately, and each one is something you have probably seen without knowing why:

Renaming a huge file is instant
You edited one row in a directory table. The data never moved. This is also why mv across filesystems is slow — there it genuinely has to copy.
Deleting a file that a program has open doesn't break the program
rm removes the name and decrements the link count. The inode survives as long as any process holds it open. This is why deleting a huge log file doesn't free disk space until you restart the service that's writing to it — a classic 3am production puzzle.
Permissions belong to the file, not to the name
They're stored in the inode. Two names for one inode always have identical permissions, because there is only one set.

Verify all of it in a real terminal:

cd ~/websites/demo
echo 'original' > a.txt
ln a.txt b.txt            # hard link — a second name for the same inode
ls -li a.txt b.txt        # -i shows inode numbers: identical, link count 2

echo 'changed' > a.txt
cat b.txt                 # "changed" — same file, of course

rm a.txt
cat b.txt                 # still there. the data outlives the name

ln -s b.txt c.txt         # symlink — a file whose *content* is a path
ls -l c.txt               # shown as c.txt -> b.txt
rm b.txt && cat c.txt      # now broken: the path it stores points at nothing
Foundation — Hard link vs symbolic link, and why you care

A hard link is another name pointing at the same inode. There is no "original"; delete any one name and the others keep working.

A symbolic link is a tiny file whose contents are a path string. Resolving it means reading that string and starting the lookup again. Delete the target and the symlink still exists but points nowhere.

This matters directly in deployment. The standard zero-downtime deploy — used by Capistrano, Deployer, and by hand on thousands of servers — is: upload the new release to releases/2026-07-31/, then atomically repoint the symlink current → that directory. The switch is one instantaneous operation, and rolling back is repointing it again. node_modules/.bin, Homebrew, and /usr/bin/php on many systems are all symlinks too.

Permissions, without the folklore

Nine bits, in three groups of three. rwx for the owning user, for the owning group, and for others. Each group is a digit 0–7, because three bits make an octal digit — that is the entire reason chmod uses those strange numbers.

The x bit means something different on a directory

On a file, x means "may be executed as a program".

On a directory, x means "may be traversed" — may be used as a step in a path. Without it you cannot cd into it or reach anything beneath it, even if you can read the directory itself. And r without x means you can list the names but cannot stat or open any of them. This pair is behind most "permission denied but the file is readable?!" confusion, and it is exactly why web servers need x on every directory along the path to your document root.

Why 777 is never the fix

Tutorials that say "just chmod -R 777 to fix the upload error" are teaching you to make every file on your server world-writable — including, on shared hosting, writable by other people's applications. If uploads fail, the correct fix is to make the directory owned by (or group-shared with) the user your web server runs as. Note this for later: it is the same instinct as "just disable CSRF to make the form work".

Paths, and the bug that lives in them

Resolving a path is mechanical: start at the root (absolute) or at the current working directory (relative), then walk each segment, with . meaning "stay" and .. meaning "go up one".

Bridge — "document root" is just a path prefix

Every web server has one setting that says: when a request for /about.html arrives, look for it under this directory. Apache calls it DocumentRoot, nginx calls it root, PHP's built-in server uses whatever directory you launched it from, and Vercel/Netlify call it your output or publish directory.

That is the entire mechanism, and it is why your course said moving controllers out of the web root improves security: files the server cannot construct a path to are files nobody can request. In a Laravel project, public/ is the document root and everything else — your app/, your .env, your vendor/ — sits above it, unreachable by URL. Sites that get this wrong leak their .env to anyone who guesses the URL.

Primary source for this lesson man 7 inode — the authoritative description of what an inode holds, including the mode bits table. Pair it with man 7 path_resolution, which is the kernel's own step-by-step algorithm for turning a path string into a file. Both are short, and reading a man page as a specification rather than a lookup is a habit worth building.
