What Am I Actually Installing?

School told you to install XAMPP and never said why. Here is the answer — and the reason you probably needed one of its five letters, not five.

35 minutesWin: never install a tool you can't justify

This lesson exists because of a fair complaint: being handed an install command you don't understand is the same problem as being handed XAMPP. So before you install anything this weekend, you should be able to say what each piece is and what would break without it.

By the end you will have installed exactly one thing.

Start with the bundle you were given

Foundation — Why XAMPP existed, honestly

It was not a scam or a teaching failure. In 2002, making Apache, MySQL and PHP work together on Windows meant editing httpd.conf by hand, getting DLL paths right, registering services, and matching version combinations that were known to conflict. It could genuinely take an afternoon and fail for reasons nobody could diagnose. XAMPP bundled a combination that was known to work. That was worth a lot.

Two things then happened. PHP 5.4 (2012) added a built-in web server — php -S — so Apache stopped being necessary for development. And SQLite made a database server optional for anything single-writer. Between them, the problem XAMPP solved largely stopped existing for learners.

The lesson to take is not "XAMPP is bad". It is: a bundle is an answer to a question. Know the question before accepting the answer — because when the question changes, the bundle silently stops making sense, and nobody tells you.

So what is PHP, as a thing on disk?

"Install PHP" sounds like installing an application. It is three files-ish, and knowing which is which explains most PHP install problems you will ever hit.

Two things this immediately explains

"Call to undefined function curl_init()" does not mean PHP is broken or that you wrote it wrong. It means the curl extension isn't loaded. php -m lists what is. Install the package, restart, done.

"It works in the terminal but not in the browser" — the classic. CLI and FPM are different SAPIs with different php.ini files: /etc/php/8.5/cli/php.ini versus /etc/php/8.5/fpm/php.ini. You enabled the extension for one door and not the other. This single fact resolves an enormous amount of otherwise inexplicable behaviour.

Build your own stack

Rather than a list to obey, work out what you need. Tick what you actually want to do and watch the toolset grow — including the moment where ticking something adds nothing.

Install checkpoint 1 — one package

This is everything you need for all of Friday and most of Saturday. Run it in your own terminal, since it needs a password prompt:

sudo apt update
sudo apt install -y php-cli

Then interrogate what you just got, rather than trusting it:

php -v                  # version, and which SAPI (you'll see "cli")
which php               # where the binary landed
ls -lh $(which php)     # how big the entire language runtime is
php -m | head -30       # which extensions are loaded — no curl, no mysql yet
php -i | grep 'Loaded Configuration'   # which php.ini is in effect

php -r 'echo "the engine works\n";'    # -r runs code directly

Now prove the claim that made Apache unnecessary:

mkdir -p ~/websites/demo && cd ~/websites/demo
echo '<h1>Hello from <?= PHP_VERSION ?></h1>' > index.php

php -S localhost:8888

Open http://localhost:8888. That is a web server, and you installed one package. No Apache, no MySQL, no Perl, no control panel — and nothing about it is a toy: it is the same engine, reached through a different door.

What you did not get, and will notice

php -m shows no curl, no mysqli, no pdo_mysql, no mbstring. That is correct and deliberate. When a lesson needs one, it will tell you which and why — and you will feel the specific thing that was missing, which is worth far more than having had it all along.

PDO's core is bundled, but its MySQL driver is not. So new PDO('sqlite:…') may work while new PDO('mysql:…') fails with "could not find driver". That message means exactly one thing: install the driver package.

Bridge — this is how you should read any stack, forever

You will meet more bundles: LAMP, LEMP (nginx instead of Apache — E for "engine-x"), MEAN, MERN, Laravel Sail, Herd, Valet, Docker Compose files with six services.

Ask the same three questions every time: What problem was this bundle solving? Is that still my problem? Which pieces do I actually use?

Sometimes the answer is "all of them" and the bundle is right — a Docker Compose file for a team of eight is a genuinely good idea. But it should be a conclusion you reached, not a default you inherited. That is the difference between operating a stack and understanding one, and it is the whole reason this lesson exists.
