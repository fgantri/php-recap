Why a Database, Not a File

You can store data in a file. People did, for years. The question is what you would have to build afterwards — and the honest answer is: a database.

35 minutesWin: name the six things you'd have to write yourself

Your course listed six properties a database gives you that a file does not. Rather than take them on trust, watch one of them fail.

Two requests, one file

A visit counter stored in count.txt. Two requests arrive at nearly the same moment. Step through and watch what each process does.

Concurrency — the failure you cannot fix in application code

The lost update

Both processes read 41, both compute 42, both write 42. Two visits, one increment. Nothing errored. No log line. The number is just quietly wrong, and it will be wrong again, unpredictably, forever.

This is a race condition, and you cannot fix it with more careful PHP — the gap between read and write exists no matter how you write it. You need something that can make read-modify-write atomic. That is what a transaction is, and building one correctly over a plain file means implementing locking, crash recovery and a write-ahead log. At which point you have written a database.

The six properties, and what each replaces

PropertyWhat it doesWhat you'd write instead
ConcurrencyMany readers and writers without corruptionLock files, and the deadlocks that come with them
TransactionsA group of changes applies entirely or not at allJournalling, rollback, crash recovery
IndexesFind one row among ten million without reading the restA B-tree, kept in sync with every write
Query languageDescribe the result; the engine plans howHand-written loops, re-optimised by hand each time
ConstraintsRules the data enforces on itselfValidation in every code path that ever writes
DurabilityCommitted data survives a crash mid-writefsync discipline and a recovery protocol
Foundation — ACID, which is these properties with a name

Atomicity — a transaction is all or nothing. Debit and credit both happen, or neither does.

Consistency — a transaction moves the database from one valid state to another; constraints are never left violated.

Isolation — concurrent transactions do not see each other's half-finished work. This is what defeats the counter above.

Durability — once committed, it survives power loss. Implemented with a write-ahead log: record the intention to disk first, apply it after, so a crash can always be replayed or undone.

You will be asked what ACID stands for in interviews. More usefully: each letter is a specific failure it prevents, and you have now watched Isolation fail.

The relational model

Edgar Codd's 1970 paper proposed something that sounds obvious now and was radical then: store data as relations — tables of rows and columns — and let a query language describe what you want, with the system deciding how to get it.

What made it win was not the tables. It was physical data independence: your query says what, so the engine is free to change how — add an index, change the join order, use a different algorithm — without you rewriting anything. Every predicted replacement has had to reinvent some version of that, which is why SQL is still here fifty-five years later.

Bridge — when relational is genuinely the wrong choice

Being able to say when not to reach for it is the mark of judgement rather than habit:

Redis — key–value in memory. Sessions, caches, rate limiters, queues. Microsecond reads; durability is optional by design.

MongoDB and friends — document stores. Genuinely useful when documents vary in shape and you rarely join. Frequently chosen to avoid designing a schema, which is a decision that arrives later as a bill.

Elasticsearch — inverted indexes for full-text search and ranking. SQL's LIKE '%term%' cannot use an index and does not rank.

SQLite — relational, but a library writing to one file rather than a server. Enormously underrated: it is the most deployed database in the world, it is what Vercel and Cloudflare's edge SQL products are built on, and for a read-heavy site it is often the right answer.

The default should be relational. Departing from it should be a decision you can defend with a specific property you need.

Install checkpoint 3 — and a genuine choice

This is the first point where a server becomes a real question rather than an assumption. You have two honest options.

SQLite — already installed

You added php-sqlite3 at checkpoint 2. Nothing more to do.

$pdo = new PDO('sqlite:' . __DIR__ . '/app.db');

No process, no port, no password, no service start. The whole database is one file you can copy, commit or delete. Every concept in the next six lessons — tables, types, keys, joins, indexes, prepared statements, transactions — works identically.

MariaDB — a real server

sudo apt install -y mariadb-server php-mysql
sudo service mariadb start

mariadb-server is the server process; php-mysql is the client driver PHP needs to speak to it. Two separate things — in production they are usually on different machines.

Choose this if your course uses MySQL, or a job will.

Which should you pick this weekend?

Install MariaDB — your course uses MySQL, so matching it means Monday costs you nothing. But install it knowing it is a choice, not a requirement, and knowing precisely what it adds over SQLite: concurrent writers, network access, and user accounts. Nothing else in these lessons depends on it.

That distinction is the whole point of this lesson's install checkpoint. "Do I need a database server, or do I need a database?" are different questions, and XAMPP never let you ask the second one.

Set it up

sudo service mariadb start
mysql -u root

CREATE DATABASE myapp CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci;
USE myapp;
SHOW TABLES;

(WSL has no systemd by default, which is why this is service rather than systemctl.)

Three levels, worth keeping straight: the server is a process listening on port 3306, exactly like the web server in Lesson 0004. A database is a named container inside it. A table is a structure inside that. You will type localhost and 3306 into a DSN in Lesson 0019.

Primary source for this lesson Codd (1970), "A Relational Model of Data for Large Shared Data Banks" — the paper that started it. Read the first two pages; the argument for data independence is stated more clearly there than in any textbook since.

For the modern practical view, SQLite's own "When To Use" page is an unusually honest document about the trade-offs of each kind of store.
