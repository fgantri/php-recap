Sockets, Ports, and the Accept Loop

"The server is running" means one process is blocked inside a function called accept(), waiting. Everything else about web servers is detail on top of that sentence.

50 minutesWin: write the four calls that are a server

Your course said: "php -S starts a long-lived process that opens a socket on port 8888 and waits." That is precisely correct and almost nobody who reads it could write one. Today you will — in about fifteen lines, using no framework and no library.

A socket is a file descriptor

Remember the file-descriptor table from Lesson 0001. A socket is an entry in it. Not a special networking object — the same integer-indexed table that holds your open files, because Unix's design principle is that everything you can read from or write to should look the same.

That is why you can read() and write() a network connection with the same calls you use on a file. And it is why the following works on your machine right now:

# bash can open a TCP socket as if it were a file
exec 3<>/dev/tcp/example.com/80
printf 'GET / HTTP/1.1\r\nHost: example.com\r\nConnection: close\r\n\r\n' >&3
cat <&3
exec 3<&-

No browser, no curl, no library. You opened a connection on file descriptor 3, wrote nine lines of text into it, and read the reply back. That is the entire web. Everything else is convenience.

Foundation — Host, port, and the four-tuple

An IP address identifies a machine. A port — a number 0–65535 — identifies which listening program on it. Your course covered both. Here is the part it left out, which resolves a question you may not have known you had.

If a hundred browsers all connect to your server on port 8888, how does the kernel keep them apart? Because a connection is identified not by one port but by a four-tuple: (source IP, source port, destination IP, destination port). Your server's side is always (your IP, 8888), but each client contributes a different random high-numbered source port. Every connection is therefore unique, and the kernel routes bytes to the right socket by looking up that whole tuple.

Ports below 1024 are privileged — only root may bind them. That is exactly why development servers use 8000, 8080 or 8888, and why a real deployment has nginx (started as root, then dropping privileges) holding port 80 while your application sits on a high port behind it.

The four calls

Every TCP server ever written, in any language, is these four calls in this order:

CallWhat it asks the kernel for
socket()Give me an endpoint. Returns a file descriptor.
bind()Reserve this address and port for it. Fails if taken → Address already in use.
listen()Start queueing incoming connections for me, up to a backlog of N.
accept()Block until one is queued, then hand me a new fd for that one conversation.

The subtle one is accept(). It returns a second socket. The original listening socket never carries data — it exists only to produce connection sockets. One shop door, many conversations.

Play the loop

Boot the server by running the syscalls in order, then throw traffic at it. Watch what happens with one worker versus four, and try adding six clients at once before you have called listen().

What the simulator is showing you

The backlog is the kernel's, not your program's. Connections are accepted by the operating system and queued before your code has any idea they exist. This is why a server that's stuck can still be connected to — the queue absorbs arrivals — and why it eventually starts refusing: the queue has a fixed size.

One slow client blocks everything behind it. With one worker, a 4-tick request makes three fast requests wait 4 ticks each. That is head-of-line blocking, and it is the single reason web servers run pools of workers. Switch to 4 workers and rerun the same traffic to feel the difference.

Write it for real

Create server.php in ~/websites/demo and type this out. Do not paste it.

server.php
<?php

$socket = stream_socket_server('tcp://127.0.0.1:8888', $errno, $errstr);

if (! $socket) {
    exit("Cannot listen: $errstr ($errno)\n");
}

echo "Listening on http://127.0.0.1:8888 — Ctrl+C to stop\n";

while (true) {
    $conn = stream_socket_accept($socket, -1);   // blocks here

    $request = fread($conn, 8192);
    $line    = strtok($request, "\r\n");

    echo "→ $line\n";

    $body = "<h1>Hello from a socket</h1><p>You asked: $line</p>";

    fwrite($conn, "HTTP/1.1 200 OK\r\n");
    fwrite($conn, "Content-Type: text/html\r\n");
    fwrite($conn, "Content-Length: " . strlen($body) . "\r\n");
    fwrite($conn, "Connection: close\r\n");
    fwrite($conn, "\r\n");
    fwrite($conn, $body);

    fclose($conn);
}

Run it with php server.php, then open http://127.0.0.1:8888 in your browser. You have written a web server. Not a toy version of one — that is what one is.

stream_socket_server collapses socket(), bind() and listen() into one call, which is why the code is shorter than the four-call story. Use strace -e trace=network php server.php on Linux to watch the real syscalls underneath — socket, bind, listen, accept4, exactly in order.

Now break it, deliberately

  1. Leave it running and start a second copy in another terminal. You get Address already in use — bind() failing, exactly as the table said. One port, one listener.
  2. Comment out the Content-Length line and reload. Chrome will hang or truncate: without a length or chunked encoding, the browser cannot tell where your response ends.
  3. Add sleep(5); before the first fwrite. Open two browser tabs at once. The second waits for the first — head-of-line blocking, on your own machine, with your own code.
Foundation — How real servers escape the blocking problem

Your loop handles one connection at a time. The three escapes, and who uses which:

Process or thread per connection. Fork a worker for each. Simple and robust — a crash takes down one worker. Memory-hungry. This is Apache's prefork MPM and, in essence, PHP-FPM.

Event loop. One process, non-blocking sockets, and a kernel call (epoll on Linux) that says "tell me which of these ten thousand sockets is ready". Enormously efficient for I/O-bound work; a single slow computation stalls everything. This is nginx, Node.js, and Redis.

Lightweight concurrency. The runtime multiplexes many cheap tasks onto few OS threads — goroutines in Go, async tasks in Rust. The programming model of threads with the cost profile of an event loop.

The classic production stack uses two of these at once: nginx (event loop) accepts thousands of slow client connections and speaks to PHP-FPM (process pool) over a fast local socket. Lesson 0007 is entirely about that handoff.

Bridge — where this shows up in the tools you named

Cloudflare runs a very large event loop close to your users; a Worker is a handler invoked from it, which is why Workers must not block. Vercel and Netlify hide the accept loop entirely and hand you a function — the same shape as the body of your while loop. WebSockets are what happens when you simply don't fclose(): the connection stays open and both sides keep writing. HTTP/2 multiplexes many logical streams over one TCP connection to dodge the head-of-line blocking you just produced with sleep(5).

You now have the one mental model that makes all four legible.
