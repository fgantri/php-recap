What frameworks add on top

Middleware pipeline

Layers each request passes through and each response passes back through — auth, CSRF, rate limiting, compression. Structurally the callback chain from Lesson 0012.

DI container

Controllers declare what they need; the container constructs and supplies it. Replaces your $db-through-shared-scope, and is what makes code testable.

ORM

Note::where('user_id', $id)->get() instead of SQL, returning objects. Eloquent is Active Record (the model persists itself); Doctrine is Data Mapper (a separate layer moves data). Genuinely different philosophies.

Migrations

Schema changes as versioned, executable code, so every environment's database rebuilds from source instead of being hand-edited in a GUI.

Validation

Declarative rules with structured errors, returning 422. You wrote the status code; they wrote the rule engine.

Composer + PSR-4

No more require for classes. Namespaces map to directories and classes load on first use — the reason Database.php must be named after its class.

Every one of those solves a problem you can now name, because you either hit it or were shown where it lies.

The thing almost nobody says out loud

An enormous amount of front-end evolution since 2015 has been rediscovering server rendering. SPAs moved rendering to the browser; first paint got slow and SEO broke; SSR was reintroduced; then hydration was found expensive; now the industry is shipping less JavaScript and rendering more on the server.

React Server Components — the current frontier — are, structurally, components that run on the server and send HTML. Which is what a PHP view has always been, with a better programming model on top.

This is not a reason to be smug. It is a reason to be calm: you now understand the axis these tools move along, so a new framework is a new position on a familiar line rather than something to learn from zero. That is exactly the fluency you said you wanted.

WordPress and Shopware, specifically

WordPress — predates the conventions

Not MVC. Its cycle goes through a query parser and a template hierarchy — fixed rules deciding which template file renders a URL (single-post.php → single.php → index.php).

Hooks are its extensibility model: add_action and add_filter register callbacks against named events. That is Lesson 0012's higher-order functions, at the scale of a whole application.

$wpdb is a global connection wrapper over direct SQL, with $wpdb->prepare() playing exactly the role Lesson 0020 described.

If WordPress has felt arbitrary, that is because its conventions predate the ones this weekend taught. Knowing both makes the differences legible instead of confusing.

Shopware 6 — Symfony underneath

Built on Symfony, so the entire Symfony column of the first table applies directly: its controllers are Symfony controllers, its templates are Twig, its DI is Symfony's container, its request cycle is HttpKernel.

On top sits its own domain layer — the DAL (Data Abstraction Layer), entity definitions, and an event system.

The practical route in: learn Symfony fundamentals. Read the HttpKernel component you were pointed at in Lesson 0014, and Shopware stops being a separate subject.

Shopify is a different animal entirely — a hosted platform with Liquid templating and no server of your own. The concepts transfer; the control does not.

Cloudflare, Vercel, and the edge

You have everything needed to read these correctly now:

  • A CDN caches responses near users. From Lesson 0006: it removes round trips, which no code optimisation can match.
  • An edge function is a request→response handler with no machine of its own. It is the body of your while loop from Lesson 0004, running in someone else's event loop — which is why blocking is forbidden there.
  • Edge KV / D1 exist because shared-nothing at the edge means truly nothing — no local disk, no local database. State must be explicitly external.
  • Vercel's build output is a manifest describing, per route, whether it is static or dynamic. That is try_files from Lesson 0007, expressed as configuration.
