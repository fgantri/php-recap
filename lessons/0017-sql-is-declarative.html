SQL Is Declarative

You never write a loop. You describe the result and the engine decides how to produce it — which is a genuinely different way of thinking, and the reason SQL has outlasted every language it was written alongside.

50 minutesWin: describe results, not steps

Everything you have written this weekend has been imperative: do this, then this, then this. SQL is declarative. You state a condition and the engine — its query planner — decides whether to scan the table, use an index, or do something cleverer.

The practical consequence, worth holding onto: a slow query is usually fixed by changing the schema, not the query. The same SQL can be a thousand times faster after adding an index, because you only ever described the what.

The clauses, in the order they actually run

SQL is written in one order and evaluated in another. Knowing the evaluation order explains several things that otherwise look arbitrary.

WrittenRunsDoes
SELECT5Choose columns; compute expressions
FROM / JOIN1Assemble the working set of rows
WHERE2Filter rows
GROUP BY3Collapse rows into groups
HAVING4Filter groups
ORDER BY6Sort the result
LIMIT7Take a slice
Foundation — Three puzzles this order solves

Why can't I use a SELECT alias in WHERE? Because WHERE runs at step 2 and the alias isn't created until step 5. It does work in ORDER BY (step 6), which is why the rules feel inconsistent until you see the order.

Why HAVING and not WHERE for counts? WHERE filters rows before grouping exists; HAVING filters the groups afterwards. WHERE COUNT(*) > 5 is asking a question about something that hasn't been computed yet.

Why is LIMIT 10 still slow? Because it runs last. If ORDER BY had to sort two million rows, LIMIT throws away 1,999,990 of them after all the work was done. An index on the sort column is what actually fixes it.

The silent join bug

An orphan row — a note whose user_id points at a deleted user — simply vanishes from an INNER JOIN. No error. No warning. Your "notes per user" report is quietly short by however many orphans exist, and the number looks entirely plausible.

This is the concrete damage that foreign key constraints prevent, and it is why Lesson 0021 argues for pushing rules into the database. A count that is wrong and looks right is worse than a crash.

Two habits worth forming now

Name your columns

SELECT * FROM notes;              -- fine in a client, bad in code
SELECT id, body, created_at FROM notes;   -- survives schema changes

SELECT * in application code breaks when someone adds a column, moves more bytes than you need, and hides what the code depends on. In a terminal, exploring, it is exactly right.

Let the database do the work

// N+1 — one query, then one more per row. 101 round trips for 100 notes.
$notes = $db->query('SELECT * FROM notes')->fetchAll();
foreach ($notes as $note) {
    $user = $db->query('SELECT name FROM users WHERE id = ?', [$note['user_id']])->fetch();
}

// One query. One round trip.
$notes = $db->query(
    'SELECT notes.*, users.name FROM notes JOIN users ON users.id = notes.user_id'
)->fetchAll();
Bridge — N+1 is the most common ORM performance bug in existence

Written by hand, the loop above is obviously wrong. Through an ORM it is invisible: $note->user->name inside a Blade loop issues a query per iteration and looks like a property access.

Every ORM has an escape: Laravel's Note::with('user')->get(), Doctrine's fetch joins, Rails' includes. They exist solely for this. Laravel 9+ can even throw on lazy loading in development — Model::preventLazyLoading() — which is worth switching on the day you start using Eloquent.

You will find this bug in production code for the rest of your career. Knowing what it looks like as SQL is what lets you spot it as ORM code.
