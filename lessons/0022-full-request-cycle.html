The Full Request Cycle

Every piece is now in place. Assembling them reveals the loop you will perform for the rest of your career — and one vulnerability that looks identical to working code.

45 minutesWin: 404 vs 403, and why it's a judgement call

The loop

This is roughly MVC. The Model layer is the piece your course did not formalise — right now raw arrays from the database play that role, and in a framework a Note class would.

The vulnerability that looks like working code

Here is the controller as your course first wrote it. It works. Every test passes. Ship it.

$note = $db->query('SELECT * FROM notes WHERE id = :id', [
    'id' => $_GET['id'],
])->fetch();

require 'views/note.view.php';

Change the number in the address bar and you are reading somebody else's notes.

IDOR — Insecure Direct Object Reference

The application exposes a database id in the URL and does not verify the requester is entitled to the object behind it. Change the number, see other people's data.

It is one of the most common vulnerabilities in real applications, precisely because the working version and the broken version look nearly identical. The query is parameterised. There is no injection. Nothing in a code review jumps out — unless you are specifically asking "who is allowed to see this?"

The fix is never to obscure or hash the id. The fix is to check ownership on every single request.

Authentication vs authorization

AuthenticationWho are you?Login, sessions, tokens, password verification401
AuthorizationAre you allowed to do this?Ownership, roles, permissions403

Separate concerns, both required. A correctly authenticated user is still not entitled to everything. (And note 401 is misnamed — it means unauthenticated. The naming has confused people since 1997.)

Two approaches, and why the second is better

Filter in the query

$note = $db->query(
    'SELECT * FROM notes WHERE user_id = :uid AND id = :id',
    ['uid' => $currentUserId, 'id' => $_GET['id']]
)->fetch();

if (! $note) { abort(404); }

Secure, and it conflates two different situations: this note doesn't exist and this note exists but isn't yours both become 404. For debugging, logging and API consumers, that difference matters.

Separate the checks

$note = $db->query('SELECT * FROM notes WHERE id = :id', [
    'id' => $_GET['id'],
])->fetch();

if (! $note) {
    abort(Response::NOT_FOUND);                       // doesn't exist
}

if ((int) $note['user_id'] !== $currentUserId) {
    abort(Response::FORBIDDEN);                       // exists, not yours
}
Note the (int) cast — this is the Lesson 0019 trap

With PDO emulating prepares, $note['user_id'] is the string '1', so '1' !== 1 is true and the rightful owner gets a 403. Either set ATTR_EMULATE_PREPARES => false on the connection, or cast at the boundary as above. Do not use != to dodge it — a loose comparison in a security check is how allowlists get bypassed.

404 or 403? The honest complication

Foundation — Correct is not always a single answer

There is a real argument on the other side. Returning 403 tells an attacker that a note with that id exists. Iterate the ids and you can map the size and shape of the dataset without reading a single record.

Which is right depends on what you are protecting:

403 when existence is not sensitive — a notes app, a blog admin. It is clearer, better for debugging, and more honest to API consumers.

404 for both when the mere existence of a record is sensitive — medical records, private repositories, HR files, anything where "there is a file about this person" is itself the leak. Log the distinction internally so you can still debug.

GitHub does exactly this: a private repository you cannot access returns 404, not 403.

This is worth internalising as a pattern of thinking, not a rule to memorise. Knowing that a trade-off exists — and being able to name what it trades — is what lets you make it deliberately rather than by accident. That is the difference between following advice and having judgement.

Magic numbers

The finished controller contains 1 and 403. Both are magic numbers — bare literals whose significance is implicit. You know today that 1 means "the current user". In six months, to a colleague, or in a codebase running five years, it is a number.

For the user id — a variable

$currentUserId = 1;
// …
if ((int) $note['user_id'] !== $currentUserId)

This deliberately breaks the "inline single-use variables" guideline. The name is doing all the work. Knowing when a guideline does not apply is more valuable than following it.

For the status — a constant

final class Response
{
    const NOT_FOUND   = 404;
    const FORBIDDEN   = 403;
    const UNAUTHORIZED = 401;
}

You will abort with these in many places; a local variable in each would be silly. When a name must be available everywhere, make one place for it.

abort(403) became abort(Response::FORBIDDEN). The behaviour is byte-for-byte identical. All that changed is that a reader no longer needs outside knowledge. That is what most of programming looks like — not grand redesigns, but a long accumulation of small changes, each making something slightly clearer.

Bridge — what frameworks add here

Laravel: policies and gates. $this->authorize('view', $note) calls a NotePolicy::view() method. Same check, moved somewhere reusable and testable.

Symfony: voters. #[IsGranted('VIEW', subject: 'note')] — an attribute on the controller, with the logic in a voter class.

Both: route–model binding turns /notes/{note} into an already-fetched Note object, and a missing one 404s before your controller runs.

The value is not that the check gets shorter. It is that it moves somewhere it can be tested in isolation and applied consistently — because an authorization check that exists in seventeen controllers is an authorization check that is missing from one of them.
