Templating and Escaping

A template engine is a function from (file, data) to string. You can write a real one in twelve lines — and once you have, Blade and Twig become obvious rather than magical.

50 minutesWin: build a template engine, and close the XSS hole your course flagged

Your course separated controllers from views using require, and noted the weakness honestly: variables reach the view through shared scope, so nothing declares what a view needs. Today you fix that, and you close the security hole Chapter 12 pointed at and Chapter 14 left open.

The mechanism: output buffering

require on a view sends its output straight to the browser. To capture it instead, you need a way to intercept everything PHP would print. That is output buffering, and it is the single feature every PHP template engine is built on.

ob_start();                 // from here, output goes into a buffer
echo 'hello';
$captured = ob_get_clean();  // take the buffer's contents and discard it

echo strtoupper($captured);  // HELLO

A real template engine, in twelve lines

src/view.php
<?php

function view(string $template, array $data = []): string
{
    $path = __DIR__ . "/../views/{$template}.view.php";

    if (! is_file($path)) {
        throw new RuntimeException("No such view: {$template}");
    }

    extract($data, EXTR_SKIP);   // keys become local variables

    ob_start();
    require $path;            // its echoes land in the buffer
    return ob_get_clean();
}

Used from a controller:

echo view('notes', [
    'heading' => 'My Notes',
    'notes'   => $notes,
]);
Four real improvements over bare require

The contract is explicit. The array at the call site is the list of what the view needs. No more guessing which variables happen to be in scope — and your editor stops underlining things.

The view is isolated. Inside the function, a view sees only what was passed plus what the function itself declares. A controller's private variables can no longer leak in and be relied upon by accident.

The output is a value. You can now wrap it in a layout, cache it, test it against an expected string, or return it as part of a JSON payload. Rendering stopped being a side effect.

Missing views fail loudly. Your course's abort() had a known hole — abort(422) would fatal because views/422.php doesn't exist. A check like this one is how you close it.

Now the dangerous part

Your course was explicit that <?= $note['body'] ?> is an XSS vulnerability and said "get into the habit now". Here is the habit, and why it is not optional.

XSS lab — you are the attacker

You are writing a note. The app renders it back to everyone who views your profile.

<?= $note ?> — raw

<?= htmlspecialchars($note) ?>

What you are actually seeing

The left pane is not "displaying" your input. It is parsing it as HTML. A <script> tag there would execute with the full privileges of the logged-in viewer — read their session cookie, post as them, change their email, exfiltrate anything on the page.

htmlspecialchars() converts < > & " ' into entities, so the parser sees characters instead of markup. Same visible text, no structural power. This is the identical principle as prepared statements in Lesson 0020: data must never be able to become code.

Escaping is context-dependent

This is the part most tutorials get wrong. htmlspecialchars is correct for HTML text — and insufficient elsewhere.

Where the value landsCorrect escapingWhat goes wrong otherwise
HTML body — <p>HERE</p>htmlspecialchars($v, ENT_QUOTES, 'UTF-8')Tag injection
Attribute — value="HERE"Same, and always quote the attributeUnquoted attributes break out on a space: x onmouseover=alert(1)
URL parameter — ?q=HEREurlencode($v)Parameter injection; broken links
Inside <script>json_encode($v, JSON_HEX_TAG|JSON_HEX_AMP)Script breakout — htmlspecialchars does not save you here
href="HERE"Escape and allowlist the schemejavascript:alert(1) is a valid URL
Inside CSSAvoid entirely; use a class nameCSS injection, data exfiltration via url()

Always pass the flags: htmlspecialchars($v, ENT_QUOTES, 'UTF-8'). Without ENT_QUOTES, single quotes pass through — and value='HERE' is then escapable. PHP 8.1 made ENT_QUOTES the default, but be explicit; you will read older code.

Make it short enough to always use:

function e(?string $value): string
{
    return htmlspecialchars($value ?? '', ENT_QUOTES, 'UTF-8');
}
<li><?= e($note['body']) ?></li>
Bridge — why Blade, Twig and React escape by default

Manual escaping fails for a structural reason: it is opt-in, so a single forgotten call is a vulnerability, and the vulnerable version is shorter to type.

So modern engines invert it. Blade's {{ $note }} escapes automatically; you must write {!! $note !!} to opt out — and that syntax is deliberately ugly so it stands out in review. Twig's {{ note }} is the same, with |raw to escape the escaping. React's JSX escapes everything, and the opt-out is called dangerouslySetInnerHTML — a name chosen so you cannot use it thoughtlessly.

Notice the shared design principle: make the safe thing the default and the dangerous thing verbose. That is worth stealing for your own APIs, and it is the strongest single argument for using a template engine at all.
