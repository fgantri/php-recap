Bytes, Programs, Processes

A file is just bytes. Something has to be willing to run them — and which something, decides everything about how you work.

30 minutesWin: why .php needs no build step

Your course opened with a claim worth taking apart: "A file on disk is a sequence of bytes. It becomes a program only when something is willing to execute those bytes." That is exactly right, and it is doing more work than it appears to.

Open a real terminal and look at some bytes:

cd ~ && mkdir -p websites/demo && cd websites/demo
echo '<?php echo "hi\n";' > hi.php

# the bytes of your PHP file
xxd hi.php | head -2

# the bytes of the program that runs it
xxd $(which php) | head -2

The first is readable text. The second begins 7f 45 4c 46 — hex for \x7fELF, the magic number that tells Linux "this is an executable". Both are files. Both are bytes. Only one of them can be handed to the CPU.

Every file format announces itself in its first few bytes. ELF for Linux executables, MZ for Windows .exe, %PDF, <?xml, PK for zip (and therefore .docx, .jar, .xlsx). The file command does nothing but read those and consult a table.

Two ways to make bytes run — and the third one nobody mentions

Your course notes give the standard pair: compiled and interpreted. That division is useful and slightly false, and the falseness is where PHP actually lives.

Foundation — "Interpreted" is a claim about packaging, not about speed

People say "PHP is slow because it's interpreted." Both halves are shaky. PHP compiles to bytecode exactly like Java does; the difference is that Java writes .class files and PHP keeps its opcodes in memory. And since PHP 5.5, OPcache caches those opcodes between requests, so the compile step usually happens once per file per deploy, not once per request.

The useful distinction is not compiled/interpreted. It is: is there an artefact between my source and the thing that runs? If yes, you have a build step, a deploy pipeline, and a gap where source and running code can disagree. If no, the file on disk is the program.

Bridge — this is the whole reason Vite exists

PHP's "no artefact" property is exactly what modern JavaScript lost. Browsers can't run TypeScript, JSX, or .vue files, so a build step must produce something they can. Every front-end build tool you've heard of — webpack, Rollup, esbuild, Vite, Turbopack — exists to make that unavoidable artefact-producing step fast enough to feel like it isn't there.

Vite's trick, worth knowing now because it will make sense of a lot later: during development it doesn't bundle. It serves your modules to the browser individually over HTTP and lets the browser's own module loader assemble them — which is to say, it works hard to recover the immediacy PHP has for free.

What a process actually is

"Run the program" is vague. What the operating system does is create a process: an isolated container with its own everything.

Look at a real one. Every process on Linux is a directory under /proc:

# start something long-lived, in the background
php -S localhost:8888 &

# the shell prints its PID; use it here
ls -l /proc/$!/fd          # its open file descriptors
cat /proc/$!/environ | tr '\0' '\n' | head   # its environment
ls -l /proc/$!/cwd         # its current directory

kill %1                    # stop it again

Those are not metaphors or teaching abstractions. That is the kernel's actual bookkeeping, exposed as files.

Foundation — fork and exec, the only two moves

Unix creates processes with a pair of calls that feel strange until they click. fork() clones the current process — same code, same memory, same open files — producing a near-identical child. exec() then replaces that child's entire memory with a different program, keeping its PID and its open file descriptors.

Every command you type does this: bash forks itself, and the child execs /usr/bin/php. That is why a child inherits your environment variables and working directory — it literally began as a copy of you. And it is why a child cannot change yours: exec replaced its memory, not yours. Lesson 0003 shows why that makes cd impossible to implement as a normal program.

The consequence that shapes all of PHP

Because each request runs in a process that is created, does its work, and is destroyed, PHP has what is called a shared-nothing architecture. No variable survives a request. No object stays in memory. Every request starts from absolute zero.

This sounds like a limitation. It is the reason PHP scaled across the entire 1990s and 2000s web: a crashed request cannot poison the next one, a memory leak cannot accumulate, and you scale by adding more processes without coordinating anything. It also explains, entirely, why sessions and caches exist — they are the workarounds for a language that deliberately forgets.

Bridge — the same idea, renamed and sold back

Node.js took the opposite bet: one long-lived process handling many requests, sharing memory between them. Faster, and now you own the leaks and the cross-request contamination.

Then serverless arrived — AWS Lambda, Vercel Functions, Cloudflare Workers — and its central promise is: your handler runs, responds, and is torn down; state must live elsewhere. That is shared-nothing, exactly, rediscovered as a billing model. PHP developers have been writing serverless functions since 1995 without the word.

Primary source for this lesson PHP Manual — Opcodes, and the OPcache book. Skim both for ten minutes; you do not need to memorise any opcode, you need to see that the list exists and that your source becomes entries in it.

For processes, Julia Evans' zines on the Linux process model are the friendliest accurate treatment anywhere.
