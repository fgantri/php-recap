Indexes and B-Trees

The difference between a query that takes 4 milliseconds and the same query taking 40 seconds is usually one line of DDL. Here is what that line builds.

40 minutesWin: predict which queries need an index

Your course gave the right analogy: an index is a book's index. Without one, finding every mention of a word means reading every page. With one, you jump straight there. Now the mechanism, because the mechanism is what tells you when it won't help.

Scan versus seek

Finding one row among a million
Foundation — Why it's a B-tree and not a binary tree

A binary tree makes one comparison per level, so a million rows needs ~20 levels. Fine in memory. Terrible on disk, because each level is a separate random read, and a random read is the expensive operation — historically a disk seek, today still an I/O round trip.

A B-tree optimises for fewer, larger reads instead. Each node fills one 16 KB page holding hundreds of keys, so one read eliminates hundreds of possibilities. Depth collapses from 20 to about 3.

The general principle worth stealing: when a resource has a high fixed cost per access, restructure to make fewer, bigger accesses. That is the same reasoning behind HTTP request batching, database connection pooling, and why N+1 queries hurt so much.

When an index does not help

This is the part that separates memorising "add an index" from understanding.

QueryIndex used?Why
WHERE email = 'a@b.c'✓Exact match — the tree's purpose

ORDER BY created_at✓Already sorted; no sort step needed
WHERE name LIKE 'And%'✓Known prefix — a range in disguise

WHERE a = 1 with index on (b, a)✕Leftmost prefix rule — b comes first
The function trap, in code you will actually write 
-- index on created_at is IGNORED: the index stores the column, not YEAR(column)
SELECT * FROM notes WHERE YEAR(created_at) = 2026;

-- same result, and the index works
SELECT * FROM notes
WHERE created_at >= '2026-01-01' AND created_at < '2027-01-01';

Wrapping an indexed column in any function disables the index. LOWER(email) = …, DATE(created_at) = …, CAST(id AS CHAR) = … — all the same mistake. Keep the bare column on one side of the comparison and transform the other side.

Composite indexes and the leftmost prefix

An index on (user_id, created_at) sorts by user_id first, then by created_at within each user. Like a phone book sorted by surname then forename.

Query filters onIndex (user_id, created_at)
user_id✓ — the leading column
user_id AND created_at✓ — both, ideal
user_id, ordered by created_at✓ — filter and sort in one pass. The best case
created_at alone✕ — you cannot find everyone born in March in a book sorted by surname

So column order is a design decision, not a formatting one. Put the column you filter by equality first, and the column you filter by range or sort by second.

Read the plan, don't guess

EXPLAIN SELECT * FROM notes WHERE user_id = 1;
ColumnLook for
typeconst / eq_ref / ref / range are fine. ALL is a full table scan

ExtraUsing index is excellent (covering index). Using filesort / Using temporary mean avoidable work

A covering index — Using index — means every column the query needs is in the index itself, so the table is never touched. Adding one more column to an index sometimes doubles a query's speed for this reason alone.

The cost side

Indexes are a trade, and the trade is real:

  • Every INSERT, UPDATE and DELETE must update every index on the table.
  • Each index consumes disk and memory, competing with data for the buffer pool.
  • More candidate indexes means more planning work, and occasionally a worse choice.

The working rule: index the columns you filter, join and sort on. Always index foreign keys. Do not index everything, and do not index a boolean column with two values.

Bridge — where this shows up outside SQL

Lesson 0011's array_flip trick is exactly this idea — turn a list you search repeatedly into a structure you look up. The hash map is the in-memory equivalent of an index.

Elasticsearch exists because B-trees cannot answer LIKE '%term%'; it builds an inverted index — word → documents containing it — which is a different structure for a different question.

Every ORM lets you write a query with no index behind it and will happily run it. Note::where('body', 'like', "%$q%")->get() is a full table scan in fluent clothing. Reading generated SQL and running EXPLAIN on it is the only way to know — which is the argument for learning SQL before an ORM, not after.
