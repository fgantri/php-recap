HTTP Is Just Text

A protocol you can type by hand. Once you have done that once, request objects, middleware and REST stop being abstractions and become obvious conveniences.

50 minutesWin: speak HTTP with no browser involved

In the last lesson you wrote nine lines of text into a socket and a web page came back. This lesson is about those nine lines: their exact grammar, why each part exists, and what your server is entitled to assume.

The grammar, in full

A request is: one request line, then zero or more header lines, then a blank line, then an optional body. That is the whole specification of the shape.

POST /notes?draft=1 HTTP/1.1      ← method, target, version
Host: localhost:8888                ← the only mandatory header in HTTP/1.1
Content-Type: application/x-www-form-urlencoded
Content-Length: 24
                                   ← blank line. headers are over.
title=Hello&body=World             ← exactly 24 bytes, as promised
Foundation — Three details that cause real bugs

Line endings are \r\n, not \n. Carriage return then line feed, inherited from teletypes. Send bare \n and tolerant servers cope while strict ones reject you. This is why your server.php used "\r\n" everywhere.

The blank line is load-bearing. It is the only thing separating headers from body. Forget it and the server reads your body as a malformed header and hangs waiting for more.

Content-Length tells the reader when to stop. TCP is a byte stream with no concept of "message" — it will happily deliver your response in three chunks with pauses between. Without a length (or Transfer-Encoding: chunked), the receiver cannot know whether more is coming. That is precisely the hang you produced by deleting the header last lesson.

Build one and watch it parse

Change the fields and watch two things move together: the literal bytes on the wire, and the superglobals your PHP code would receive. Those superglobals are derived — PHP parses this text and hands you the pieces.

The thing to notice

$_GET is not "the GET request". It is the query string, parsed. A POST request with ?id=17 in its URL fills $_GET too. The names are a historical accident and they mislead people for years — the accurate names would be $_QUERY and $_BODY.

Do it for real, with no client library

Start your server.php from Lesson 0004 in one terminal, then in another:

# the polite way
curl -v http://127.0.0.1:8888/notes?id=17

# the honest way — you are the browser now
printf 'GET /notes?id=17 HTTP/1.1\r\nHost: localhost\r\nConnection: close\r\n\r\n' \
  | nc 127.0.0.1 8888

# see the response headers only
curl -sI http://127.0.0.1:8888/

If nc is missing, sudo apt install netcat-openbsd. The printf version is worth doing at least once: there is no library between you and the protocol, and the protocol turns out to be typing.

Methods: a contract you can break, and shouldn't

The method is a verb stating your intent. Nothing in the protocol forces a server to honour it — the constraints are promises, and breaking them breaks the rest of the web's assumptions about you.

Safe
Changes nothing on the server. A caller may issue it freely, and any number of times.
Idempotent
Doing it N times leaves the same state as doing it once. This is what makes automatic retry possible — and every load balancer, HTTP client and mobile network retries.
The classic disaster

In 2006 a company built an admin panel where every destructive action was a GET link — /admin/delete?id=5. A well-behaved crawler followed every link on the page, because that is exactly what GET promises is safe to do, and emptied the database. The crawler was correct. The application had lied about its verbs.

Status codes: the first digit is the sentence

Your course listed the five classes. The distinction that matters most in practice:

4xx means the request was wrong. 5xx means we were wrong. Get this backwards and your monitoring lies to you — a 200 page reading "not found" will be indexed by search engines, and a 500 for a user's typo will page someone at 3am.

Stateless — the constraint everything else works around

HTTP has no memory. Each request arrives with no knowledge of any previous one. The server cannot tell whether this is your first visit or your thousandth, unless the request itself carries something that says so.

Every "stateful" feature you have ever used is a workaround built on that: cookies attach a value the browser resends, sessions turn that value into a server-side lookup, JWTs sign the state and put it in the client, and caches key off the request because there is nothing else to key off. Lesson 0023 builds all of it.

Bridge — statelessness is why the modern stack looks like it does

Because every request is self-contained, any server can handle any request. That is what makes horizontal scaling, load balancers, CDNs and edge compute possible at all. Cloudflare can run your code in Frankfurt for one request and Singapore for the next precisely because the protocol promised the second one wouldn't depend on the first.

It is also why "sticky sessions" are considered a smell: they reintroduce the dependency the protocol was designed to remove, and every scaling problem afterwards traces back to it.
