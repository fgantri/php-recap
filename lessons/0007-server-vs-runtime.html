Web Server vs Application Runtime

Two programs, not one. Knowing where the boundary sits explains 502s, .htaccess, the front controller pattern, and why php -S must never see production traffic.

45 minutesWin: what nginx does that php -S doesn't

Your course used php -S and noted, correctly, that it is "a development convenience, not built for production traffic". Here is what that sentence is hiding — and it is the piece of the stack that most working PHP developers never quite learn.

The fork in the road

Every request that reaches a web server hits one decision:

Why two programs at all?

Because the two jobs have opposite requirements, and Lesson 0004 already showed you why.

Serving a file is I/O-bound and trivial: thousands of concurrent, mostly-idle connections. That is exactly what an event loop is good at, and it is what nginx is. Running your code is CPU-bound and stateful, needs isolation so one crash cannot take down the rest, and PHP's shared-nothing model wants a fresh world per request. That is what a process pool is good at, and it is what PHP-FPM is.

So the production stack uses each for what it is good at, and connects them with a fast local socket.

Foundation — CGI, FastCGI, and where PHP-FPM came from

CGI (1993). The original answer: for each dynamic request, the web server forks a brand-new process, passes the request as environment variables, and reads the response from its stdout. Beautifully simple. Catastrophically slow — a whole process spawn per request.

FastCGI. Same idea, one fix: keep the processes alive and talk to them over a persistent socket using a small binary protocol. No spawn per request.

PHP-FPM — FastCGI Process Manager — is PHP's implementation: a supervisor holding a pool of PHP workers, restarting them when they die or after N requests, and scaling the pool under load.

And here is the payoff: those CGI environment variables never went away. REQUEST_METHOD, QUERY_STRING, REQUEST_URI, HTTP_USER_AGENT — the exact keys you saw in $_SERVER in Lesson 0005 — are the CGI variable names from 1993. Every time you read $_SERVER, you are reading a thirty-year-old interface between two separate programs. That is why the naming is so strange, and why headers get mangled into HTTP_ + uppercase.

Reading the errors this creates

Two programs connected by a socket means a new class of failure that has nothing to do with your code:

502 Bad Gateway — nginx could not reach PHP-FPM, or got garbage back. PHP-FPM is stopped, or the socket path in your nginx config doesn't match the one in the pool config. Check systemctl status php8.4-fpm first, always.

504 Gateway Timeout — nginx connected fine and waited longer than fastcgi_read_timeout. Your code is genuinely too slow, or it is hung on a query or an external API.

Blank white page, HTTP 200 — PHP hit a fatal error with display_errors off. The real message is in the PHP-FPM error log, not nginx's. Knowing which of the two logs to open is most of the diagnosis.

The routing game

This is a simplified but faithful nginx try_files. Type a request path and watch the server decide. Note especially what happens to /notes/17.

nginx — request routing

Config

root /var/www/public;
index index.php;

location / {
  try_files $uri $uri/ /index.php;
}

location ~ \.php$ {
  fastcgi_pass php-fpm:9000;
}

Files on disk

/var/www/public/
  index.php
  style.css
  logo.png
  about.html
  uploads/
    cat.jpg

Request

You have just seen the front controller, from the server's side

try_files $uri $uri/ /index.php reads as: try the path as a file; then as a directory; and if neither exists, give up and hand everything to index.php.

That last fallback is what makes clean URLs possible. There is no file at /notes/17 and there never will be — nginx gives up, index.php runs, and your PHP decides what /notes/17 means by reading $_SERVER['REQUEST_URI'].

Your course said PHP's built-in server "does something close enough by default: it serves a file if one matches, and otherwise falls back to index.php." Now you know exactly which production directive it is imitating — and that in Apache the same thing is a mod_rewrite rule in .htaccess, which is the mechanism WordPress permalinks are built on.

Why php -S must not face the public

php -Snginx + PHP-FPM
ConcurrencyOne request at a time by defaultThousands of connections, a pool of workers
Static filesServed by PHP itself — slowlyServed by the kernel via sendfile
TLSNone. No HTTPS at allTerminates TLS, manages certificates
Crash isolationThe process dies; the site is downFPM restarts the worker; nobody notices
Slow clientsOccupies the only workerBuffered by nginx; PHP is never exposed to them
LimitsNone — no timeouts, no body caps, no rate limitsConfigurable at every layer

The upstream documentation states it flatly: the built-in server "is not intended to be a full-featured web server. It should not be used on a public network." That is not caution — a single slow client stalls your entire site, which you demonstrated yourself with sleep(5) in Lesson 0004.

Install checkpoint 4 — optional, and genuinely worth it once

You do not need this for any lesson or project. But wiring nginx to PHP-FPM by hand, once, converts this lesson from a diagram into something you have actually operated — and it is the single most under-explained piece of the PHP stack.

sudo apt install -y nginx php-fpm
sudo service php8.5-fpm start
sudo service nginx start

# the two halves that must agree — compare the socket paths
grep -r 'listen' /etc/php/8.5/fpm/pool.d/www.conf | head -3
grep -rn 'fastcgi_pass' /etc/nginx/

Those two paths matching is the entire difference between a working site and 502 Bad Gateway. Note that installing php-fpm adds a second SAPI alongside php-cli — same engine, different front door, and its own php.ini at /etc/php/8.5/fpm/php.ini. That is Lesson 0000's "works in the terminal but not the browser" made concrete.

Ask me to walk you through the vhost config when you get here — it is fiddly, and doing it with help beats copy-pasting a snippet you can't read.

Bridge — the same boundary, in every stack you named

WordPress ships an .htaccess whose rewrite rules are Apache's version of try_files — which is why "permalinks broke after moving hosts" is always a rewrite-rule problem, never a WordPress one.

Laravel and Symfony both put public/index.php as the document root, with everything else above it. Same pattern, same reason.

Next.js and Vite keep the boundary but move it: static assets from a CDN edge, dynamic routes to a function. Vercel's whole build output is a manifest describing exactly this static-or-dynamic decision, per route.

Cloudflare Workers collapse it — your code is the server, running in the event loop rather than behind it, which is why blocking work is forbidden there.

The vocabulary changes. The decision does not.
