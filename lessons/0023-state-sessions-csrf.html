State: Cookies, Sessions, POST, CSRF

Your course stopped before all of this and said so honestly. It is the largest gap, and it is where the most dangerous mistakes live.

55 minutesWin: how a stateless protocol remembers you

HTTP has no memory. Each request arrives knowing nothing about any previous one. So how does a site know you are logged in?

It doesn't. Your browser tells it, every single time.

The mechanism, in four steps

Doing it correctly

session_set_cookie_params([
    'httponly' => true,     // JavaScript cannot read it — blunts XSS cookie theft
    'secure'   => true,     // HTTPS only, never sent in clear
    'samesite' => 'Lax',    // withheld on cross-site POSTs — CSRF mitigation
    'path'     => '/',
]);
session_start();

// on successful login
session_regenerate_id(true);          // prevents session fixation
$_SESSION['user_id'] = $user['id'];
Foundation — Why session_regenerate_id matters

Session fixation: an attacker visits your site, gets a session id, then tricks a victim into using that same id — via a link like ?PHPSESSID=known, or by setting the cookie from a subdomain they control. The victim logs in. The session the attacker already holds is now an authenticated session.

Regenerating the id at the moment of login destroys the old one, so whatever the attacker holds becomes worthless. One line, and it closes an entire attack class. Do it on every privilege change, not only login.

Passwords

$hash = password_hash($plain, PASSWORD_DEFAULT);   // salt generated and stored for you

if (password_verify($plain, $user['password'])) { … }
Four things that are simply not negotiable

Never md5, sha1 or sha256. They are designed to be fast, which is exactly backwards — a modern GPU tries billions of sha256 guesses per second. password_hash uses bcrypt or argon2, which are deliberately slow and memory-hard.

Never your own salting scheme. password_hash generates a random salt and stores it inside the hash string. There is nothing for you to manage.

Never === on hashes. Use password_verify, which is constant-time. String comparison returns faster on an early mismatch, and that timing is measurable.

Column must be VARCHAR(255). Not 60. The algorithm's output length changes between PHP versions, and a too-short column truncates silently — locking every user out with no error anywhere.

POST, and the refresh problem

Everything your course did was GET. Forms need POST, and POST brings a problem you have certainly seen:

// naive: render the result directly from the POST handler
if ($request->method === 'POST') {
    $db->query('INSERT INTO notes (user_id, body) VALUES (?, ?)', [$uid, $body]);
    echo view('notes/index', [...]);       // ← refresh re-submits!
}

The browser remembers the last request. Refresh, and it re-sends the POST — creating a second note. Hit back, and you get "Confirm Form Resubmission". On a checkout page this is a double charge.

Post/Redirect/Get

if ($request->method === 'POST') {
    $db->query('INSERT INTO notes (user_id, body) VALUES (?, ?)', [$uid, $body]);

    $_SESSION['flash'] = 'Note created';

    header('Location: /notes', true, 303);
    exit;                                     // nothing after a redirect
}

The response to the POST is a redirect, so the page the user ends on was reached by GET. Refreshing repeats the GET — harmless. This is why flash messages exist: the success message must survive one redirect, so it goes in the session and is deleted after being read once.

303 See Other is the strictly correct status: it tells the browser to follow with GET regardless of the original method. 302 works in practice because browsers do the same thing anyway.

CSRF — the attack that needs no access to your site

CSRF — you are visiting a malicious page

You're logged into bank.example in one tab. In another, you open a forum post containing this: 

<!-- evil.example -->
<form action="https://bank.example/transfer" method="POST" id="f">
  <input type="hidden" name="to"     value="attacker">
  <input type="hidden" name="amount" value="5000">
</form>
<script>document.getElementById('f').submit();</script>

Why it works

The browser attaches cookies based on the destination, not the origin. A request to bank.example gets bank.example's cookies — regardless of which page caused it. So the forged request is fully authenticated.

The attacker never sees the response. They do not need to. Causing the action is the whole attack.

Note what does not help: HTTPS (the request is legitimately encrypted), checking the session (there genuinely is one), rate limiting, or a strong password.

The defence

// once per session
$_SESSION['csrf'] ??= bin2hex(random_bytes(32));

// in every state-changing form
<input type="hidden" name="_token" value="<?= e($_SESSION['csrf']) ?>">

// before acting on any POST/PUT/PATCH/DELETE
if (! hash_equals($_SESSION['csrf'], $_POST['_token'] ?? '')) {
    abort(419);
}

The attacker's page cannot read your token — the same-origin policy forbids evil.example from reading bank.example's HTML. They can cause a request; they cannot construct a valid one.

DetailWhy
random_bytes, not rand()Cryptographically secure. rand() and mt_rand() are predictable from a few outputs
hash_equals, not ===Constant time. === returns early on the first differing byte, and that timing leaks the token
State-changing methods onlyGET should never change state — if it does, you have a much bigger problem
SameSite=Lax as wellDefence in depth. Good, but not sufficient alone: it varies by browser and doesn't cover every case
Bridge — why you have typed @csrf without knowing why

Laravel's @csrf emits exactly that hidden input, and VerifyCsrfToken middleware performs exactly that hash_equals. Symfony's csrf_token() and Django's {% csrf_token %} are the same thing.

The 419 status Laravel returns is not a real HTTP code — it is Laravel's own "Page Expired", chosen because the usual cause is a genuinely stale token after leaving a tab open, not an attack.

APIs using bearer tokens don't need CSRF protection, because the browser doesn't attach an Authorization header automatically — the attack depends entirely on automatic credential attachment. Cookie-authenticated APIs absolutely do need it. Knowing which you are building is the whole question.
