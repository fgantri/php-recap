The Shell, Properly

The shell is a programming language whose data type is "process". Once you see it that way, PATH, pipes, exit codes and environment variables stop being trivia and become one mechanism.

50 minutesWin: resolve a command the way bash does

Your course gave you four words — terminal, shell, command, process — and drew the line between them correctly. Here is what it costs to actually own that distinction: when you type php -S localhost:8888 and press Enter, eleven distinct things happen before PHP prints anything. Knowing them is the difference between "it says command not found" being a mystery and being a two-second diagnosis.

What Enter actually triggers

Foundation — Step 8 is the whole of "command not found"

PATH is a single string of directories separated by colons. Bash splits it, and tries each directory in order, looking for a file with your command's name that has the execute bit set. First match wins; the rest are never consulted.

Two things fall out of "first match wins". One: if you have two PHP versions installed, the one earlier in PATH is the one you get, which is the entire mechanism behind version managers like nvm and asdf — they do nothing but reorder PATH. Two: putting . (the current directory) in your PATH is a genuine security hole, because anyone who can drop a file called ls in a directory you visit now runs code as you.

Prove the mechanism on your real machine:

echo $PATH | tr ':' '\n'      # the search list, one per line, in order
which php                     # the first match
type php                      # same, but tells you if it's a builtin/alias
type cd                       # "cd is a shell builtin" — no file exists
type -a php                   # EVERY match, in search order
command -v php                # the portable, script-safe version
Bash caches successful lookups in a hash table, so it doesn't re-walk PATH every time. If you install a new binary and bash insists it's still missing, hash -r clears that cache. This is the answer to a specific, maddening bug that most people solve by opening a new terminal.

Why cd cannot be a program

This is the sharpest illustration of the process model from Lesson 0001, and it is worth being able to explain cold.

Suppose /bin/cd existed. You type cd /tmp. Bash forks, the child execs /bin/cd, the child changes its own working directory to /tmp, and then the child exits. Your shell — the parent — never moved. The command would be a no-op with extra steps.

A process cannot change its parent's state. So cd must be executed by the shell itself, in the shell's own process. That is what "builtin" means. The same reasoning makes export, source, exit and alias builtins too.

The pattern to carry

Whenever you wonder "why can't this program change that thing?", the answer is usually a boundary: process memory, a fork, a network hop, or a security context. Frameworks have exactly the same shape — a middleware can change the request it passes down, but it cannot reach back and change one that already went past.

Three streams, and why errors don't disappear

Every process is born with three file descriptors already open — the same numbered table from Lesson 0001:

fdNameDefaultRedirect with
0stdinyour keyboard< file
1stdout — resultsyour screen> file, >> file
2stderr — diagnosticsyour screen2> file

Two separate output streams that both land on your screen by default is a design that confuses everyone once. The point is that they can be separated:

php broken.php > output.txt          # errors still print — they went to fd 2
php broken.php > output.txt 2>&1     # "make fd 2 go wherever fd 1 goes"
php broken.php 2> errors.log         # results on screen, errors in a file
php broken.php 2> /dev/null          # discard errors entirely

A pipe connects one process's stdout to the next one's stdin — and only stdout. That is the rule people trip over: grep in a pipeline never sees error messages, because errors travel on fd 2 and the pipe only carries fd 1.

Bridge — this is why your Docker and CI logs look the way they do

The convention "results on stdout, diagnostics on stderr" is what makes tooling composable. A CLI that prints progress messages to stdout poisons every pipeline it's used in. It's also why containers log to stdout/stderr rather than to files — the orchestrator captures the streams and routes them, which is Twelve-Factor factor XI: treat logs as event streams, never as files you manage.

Exit codes: the return value of a process

Every process returns a single integer when it dies. Zero means success. Anything else means a failure, and the specific number is the program's business.

ls /nonexistent
echo $?          # 2 — ls's code for "serious trouble"

grep -q php notes.txt
echo $?          # 0 if found, 1 if not — grep uses the code as its answer

Zero-means-success feels backwards until you see why: there is exactly one way to succeed and many distinct ways to fail, so the interesting information is in the non-zero values. && runs the next command only on zero; || only on non-zero. That is all make, CI pipelines, and every deploy script are built on — and it's why a script that ignores exit codes will happily deploy a build that failed to compile.

Quoting — the same idea as PHP's quotes, one layer down

Your course covered single vs double quotes in PHP: doubles interpolate variables, singles are literal. Bash has exactly the same rule, and noticing that it is the same rule is worth more than memorising either one.

name=world
echo "hello $name"     # hello world  — expanded
echo 'hello $name'     # hello $name  — literal

The general principle underneath both: a quoting mechanism marks a region as data rather than code. That is the same sentence that will describe prepared statements in Lesson 0020 and HTML escaping in Lesson 0013. Every injection vulnerability in existence is a failure of this boundary — and you have now met it in three languages before meeting the attack.
