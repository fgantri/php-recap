Arrays Are Hash Maps

PHP has one array type where other languages have three. Knowing what it really is turns "which function should I use" into a cost calculation you can do in your head.

45 minutesWin: know the cost of every array operation

Your course said it exactly: PHP's array is an ordered hash map, serving as list and dictionary at once. That single sentence has consequences the course didn't have room for — including one that makes a loop go from instant to unusable.

How a key finds its value

A hash function turns your key into a number. That number, modulo the table size, is a slot. Look in the slot, and there is your value — in roughly the same time whether the array holds ten entries or ten million.

Foundation — Collisions, and why lookup is still fast

Two different keys can hash to the same slot. That is a collision, and it is unavoidable — you are mapping infinitely many possible keys onto a finite number of slots.

PHP handles it by chaining: the slot holds a linked list, and lookup walks it comparing actual keys. With a good hash function collisions are rare, so the average chain is near length 1 and lookup is O(1) on average. In the pathological case where every key collides, it degrades to O(n) — which is a real attack (hash-flooding), and why PHP randomises its string hash seed per process.

The optimisation that changes everything: packed arrays

Since PHP 7, an array whose keys are sequential integers starting at 0 — that is, an ordinary list — skips the hash table entirely. PHP stores the values in a flat contiguous block and uses the index as a direct offset, exactly like a C array.

$packed = ['a', 'b', 'c'];              // packed: flat memory, fast, small
$packed[] = 'd';                          // still packed

$hashed = ['a', 'b', 'c'];
$hashed[100] = 'd';                       // gap! converts to a real hash table

unset($packed[0]);                        // also converts — keys are no longer 0..n

This is why array_values() after array_filter() is more than cosmetic. Your course flagged that array_filter preserves keys, giving you [2 => 'c']. That array is now hashed — bigger and slower — and array_values() repacks it.

The O(n²) loop, which you will write at least once 
// 10,000 orders, 10,000 known ids → 100,000,000 comparisons
foreach ($orders as $order) {
    if (in_array($order['id'], $knownIds)) { ... }
}

// Flip the array once; every lookup is now a hash hit
$known = array_flip($knownIds);
foreach ($orders as $order) {
    if (isset($known[$order['id']])) { ... }
}

Seconds become milliseconds. The technique — turn a list you search repeatedly into a set you look up — is one of the highest-value habits in everyday programming, and it applies in every language.

The foreach trap

Your course noted that foreach iterates a copy, which prevents a family of bugs. True — with one exception that creates a much nastier one:

foreach ($items as &$item) {
    $item = strtoupper($item);
}
// $item is STILL a reference to the last element here

foreach ($items as $item) { }   // this overwrites the last element, repeatedly

With ['a','b','c'] you end up with ['A','B','B']. The reference outlives the loop, so the second foreach assigns into the last slot on every pass. Always unset($item); after a by-reference foreach — or avoid & entirely and use array_map.

Bridge — one array type is a real design decision

JavaScript separates Array (indexed, ordered) from Object and Map (keyed). Python separates list from dict. PHP fuses them, which is why json_encode has to guess: sequential integer keys become a JSON array [...], anything else becomes an object {...}.

That guess is a genuine source of API bugs. Filter a list, forget array_values(), and your endpoint silently changes shape from [{...}] to {"2":{...}} — breaking every client. Use JSON_PRETTY_PRINT and look at the output when you build an API; it takes ten seconds and catches this class of bug permanently.
